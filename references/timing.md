# 時間制限・失効・再認証を実際に検証する

2.2.1、2.2.3、2.2.5、2.2.6は、同じタイマーを見ても確認する条件が違う。基準ごとの[本文・公式解説](INDEX.md)と公開Testsを読み、対象ページでどの制限・データ・活動を確認するか具体化する。

## 起点と全対象を調べる

クライアントのタイマーだけでなく、サーバーの認証、予約・カート・入力の有効期限、更新、別のログインによる失効等を列挙する。無操作の定義、どの操作で期限が戻るか、警告の出方、データを失う時点、回復経路を調べる。ネットワーク監視や画面取得そのものが期限を戻さないことも確認する。

通常の設定値、資料上の期間、実際に待って測った期間を分ける。ブラウザーの仮想時計、テスト用の強制失効、短縮設定で経路を調べた場合、その操作を記録し、通常の待ち時間・警告時間・保存期間を実測したことにしない。必要なら通常設定でも実行する。

実行には単調増加時計の開始・終了時刻とUTC、ブラウザーの時刻、画面に警告が現れた時刻、実際の失効を記録する。一定間隔で観察する場合は間隔と不確かさを残す。OSの時刻変更、ページの非表示化やスリープ、タイマーの抑制、背景通信等による差も確認する。

## 2.2.1の経路を確かめる

時間制限ごとに、本文が認めるいずれか一つの経路又は例外を確認する。無効化・調整・延長を全て必須にしない。

| 採用する経路 | 対象ページで実行する確認 |
| --- | --- |
| 無効化 | 制限に遭遇する前に利用できる仕組みを操作し、元の期限を超えても失効せず、活動を完了できるか確かめる。仕組みへ到達する前に時間切れにならないかも調べる。 |
| 調整 | 既定値と、少なくともその10倍までの設定範囲を確認する。変更して元の期限を超え、設定した期限が実際の動作に反映されるか確かめる。ラベルの数字だけで終えない。 |
| 延長 | 警告が実際に利用可能になってから失効まで少なくとも20秒あるか測る。簡単な操作で、少なくとも10回実際に延長し、各回の期限と活動の保持を確認する。延長回数の上限も調べる。 |
| 例外 | リアルタイムイベント、本質的な制限、20時間超等のうち採用する条件を本文・定義と事実に照合する。「セキュリティのため」という説明だけを例外の証明にしない。 |

G198、G180、SCR1/SCR16、G133等は[関連する公開Tests](tests/2.2.1.md)を参照する。上限を調べず一回だけ延長したことや、警告要素がDOMに存在することだけで基準全体を通過にしない。

## 再認証とデータ保持を確かめる

2.2.5では、識別できる値を文字列、複数行、選択、チェック等へ入力し、変更・入力途中の状態と活動の文脈を保存する。機密の実データは使わず、許可された試験データを用意する。

実際のセッション失効を待って送信し、再認証要求を確認する。再認証後に元の各値と位置を比較し、追加の変更も行い、活動を最後まで完了する。成功画面と受け取った結果まで照合する。ログイン画面が開いた、DOMに値が残っていた、再認証した、という途中結果で止めない。別の失効原因や保存対象があれば、その経路も検査する。

[G105/G181/F12のTests](tests/2.2.5.md)を参照する。G181の特定の保存方法を、本文が全実装へ要求する条件へ増やさない。再認証でデータを保てても、2.2.1の時間制限の条件は別に検査する。

## 無操作時間の告知とAAAを区別する

2.2.6では、無操作により実際にデータを失うか、活動の開始時にその無操作時間を利用者が知れるかを確認する。2.2.1の期限直前の警告だけを、期間の告知へ置き換えない。20時間超の保存に依拠する場合、何がどこにどの条件で残るか、仕様と実際の保存期限を確認する。短い待機だけから20時間超の保存を実証しない。

無操作によるデータ損失がないとする場合も、全ての制限・保存対象・回復経路を調べて不在の根拠を残す。単にタイムアウトを観察しなかった場合は対象外にしない。利用者自身によるブラウザーの終了等は、本文・解説の適用範囲に照合する。

2.2.3の例外は非インタラクティブな同期メディア又は定義に沿うリアルタイムイベント。Aの本質性・20時間超の例外や、10回延長できることだけをAAAの通過理由にしない。時間をかけて利用する経路でも、活動を完了できるか確認する。

## 方法の準備と証拠

対象プロジェクトの起動・認証・値の投入・待機・再認証・完了の経路を[検証環境の仕様](../assets/project-methods-template.md)へ記す。既存の収集器では`wait_for`による表示待ちと各操作のUTC等を記録できるが、短い待機上限や単発画像だけで長期間を検証したことにしない。長い実行はチェックポイントを保存し、途中停止は未完了として残す。

確認した例と限界は[所有する試験サービスでの実行](../validation/timing/README.md)を参照する。そこでは実時間とサーバーの失効を用い、時計の早送りやDOMの状態書き換えを使わない。試験サービスの値や結果を依頼されたサイトへ流用せず、そのサイトの通常設定で検証方法を具体化する。
