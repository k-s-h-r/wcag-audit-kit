# 開発タスクを追加・整理する

このリポジトリの開発者向けスキル。利用者の明示呼び出しから、依頼された範囲のタスク文書を整える。成果物は`docs/tasks/`の担当ファイルと索引、必要なロードマップ更新、新しいADRを含むPRである。案や確認だけを求められた場合は、提案と指摘を返す。

## 現在地と依頼の根拠を確認する

Gitのリポジトリルートを作業の基準とする。このフォルダーの3階層上にある[AGENTS.md](../../../AGENTS.md)、[開発計画](../../../docs/ROADMAP.md)、[タスク一覧](../../../docs/tasks/README.md)を読み、責務や配置に関わる変更では[設計方針](../../../docs/SKILL-DESIGN.md)も確認する。

一覧から関連するタスクと、その前提・完了根拠・検証記録を読む。タイトルだけで重複を判断しない。Gitの作業差分、起点、関連PRの状態も確認する。関係のない全run・画像・基準資料を一度に読み込まない。新しいセッションでも、会話にしかない判断を前提にしない。

追加する作業には、利用者の依頼、目標に必要だが未着手の工程、実測された不備、前提不足で進めない作業のいずれかを根拠として付ける。記録にない不備や未実施の試験結果は作らない。根拠が弱い将来案は保留事項として残し、実装タスクを増やし続けない。

## 既存タスクを使うか、追加するかを判断する

| 状況 | 行うこと |
| --- | --- |
| 既存の未完了タスクと目的・成果物・完了条件が重なる | 既存タスクを具体化し、重複する新規タスクは作らない |
| 一つのタスクに独立した成果物や異なる担当範囲が混在する | 子タスクへ分け、親に分割理由・子ID・残る完了条件を記す |
| 複数タスクが同じ成果物と変更箇所を持ち、分ける理由がない | 代表タスクへ統合し、元のIDと経緯を参照できる状態で残す |
| 完了した作業に追加の要件や新しい不備が生じた | 完了根拠を保持し、元タスクを参照する新規タスクを作る |
| 既存タスクで扱えない必要な作業がある | 根拠を付けて新しいIDで追加する |

IDは既存ファイルと索引、確認できる未マージPRの新規タスクを調べ、最大番号の次から採番する。`T001`のように最低3桁で表記し、999の次は`T1000`とする。廃止・統合・完了したIDは再利用しない。並行する計画変更では採番を一人にまとめ、重複があれば未マージの新規IDと参照を調整する。

タスク整理だけを行うPRのために、管理タスクを再帰的に追加しない。変更対象のタスクへ整理の根拠を残せる。スキルや実装を新しく作る依頼は、必要なら独立した開発タスクとして記録する。

## 完了条件と並行できる範囲を定める

新規タスクには[テンプレート](assets/task-template.md)を使う。追加理由、前提、具体的な成果物、観察可能な完了条件、担当ファイル・共有箇所、確認方法、保存先、次の担当への引き継ぎを記す。実測を始める前に、未知の修正方法を決めつけない。

依存するタスクはIDで参照し、G1・G2等の合流条件も含めて、存在しない前提・自己参照・循環がないか確認する。親を子へ分割した場合は、後続タスクと合流条件が参照する相手も見直す。子が親に依存し、親が子を待つ循環を作らない。合流条件を満たしていないタスクを開始可能としない。

並行できる組は、入力となる前提が揃い、成果物と編集箇所が独立しているものから選ぶ。同じCLI入口・採点器・スキル指示・共有台帳を変える作業は、担当か実施順序を決める。同じブラウザー、認証、試験データ、実SR用デスクトップも共有資源として扱う。別worktree・ブランチ・runを使う前提を引き継ぐ。

測定と修正は、変更前の成績が残る単位に分ける。成果物を記録できたことと能力の達成を分け、未実施・判断保留・人への引き継ぎを成功にしない。小さな機械検査で安定した範囲から、複数ページ・AI・実SRへ広げる順序を維持する。実測や明示的な方針変更に根拠があれば、ロードマップと新しいADRで説明する。

並行可能なタスクを示すことと、担当セッションを起動することは別の操作である。このスキルのタスク計画だけの依頼から、開発の実行、チャットやエージェントの起動、監査を開始しない。実行も依頼されている場合は、その明示範囲に従う。

## 保存・確認してPRへまとめる

担当ファイルの状態と、索引の題名・開始条件・参照先を揃える。分割・統合で古いファイルを消さず、後継と経緯を残す。進捗を変える場合は実際の証拠を参照する。段階・優先順位・次の作業が変わった場合はロードマップも更新し、変わらない場合はタスク側だけで記録する。

変更後に、IDの一意性、ファイルと索引の対応、前提・合流条件を含む依存関係、相対リンク、完了条件と担当範囲を確認する。追加後にも、どれが今着手でき、どれを待つか説明できることを確かめる。タスク作成数や同時実行数の固定値を目的にしない。

作業ブランチで変更し、着手時に調整した番号で新しいADRを作成する。過去のADR、保存済みの判定・スナップショット・原始証拠は保持する。関連する確認結果と未確認事項を添えたPRを作成し、依頼なしにマージしない。GitHub Issue等への転記は依頼された場合に行う。

利用者には、追加・更新したIDと理由、今着手できるタスク、並行できる組、共有箇所の調整、残る前提、保存先とPRを簡潔に伝える。
