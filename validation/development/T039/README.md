# ダイアログ離脱の採点で証拠を照合する

変更前 `9fcaa0d` と変更後 `f68e51d` の採点器で、公開済みT030の4ページの証拠を読み直した。真正な039では両幅で離脱を確認し、040では両幅で問題を検出した。公開されている4ページの採点行はすべて一致した。[原始証拠](../T030/run-003/dialog-evidence.zip) · [比較結果](run-001/results.json)

040を別の場所へ複写し、PC幅の `dialog-focus.json`、`input-events.json`、`transition.json` の末尾にそれぞれ空白を追加した。どのコピーもJSONとして読み取った値は同じで、元のSHA-256と異なった。台帳からPC幅の入力記録の登録を外したコピーも用意した。変更前の採点はすべての対照で両幅の離脱候補を採用した。変更後は各対照のPC幅の候補が外れ、狭い幅で確認できた問題により行全体の検出は維持された。両幅の入力記録を変更した対照は、到達・判定なしになった。[コピー別の結果とSHA-256](run-001/results.json)

PC幅の遷移ファイルが途中で切れたコピーと欠けたコピーでは、変更前の採点が遷移の読み込み時点で停止した。変更後はその遷移を除外し、別の正常な経路からの到達と狭い幅の判定を維持した。元の帳票にあった指摘は採点未対応候補に残り、離脱の採点結果と区別できる。[読み込み前の照合結果](run-001/results.json)

新しい採点器でT030の保存済み76ページ・87行と、変更前の統合版の76ページ・87行をそれぞれ再採点した。各結果JSONは公開済みの内容と完全に一致した。別エージェントも、両幅と3ファイルへの改変、台帳登録の欠落、`isTrusted` を偽にしてSHA-256を再計算した入力、遷移が破損または欠落した対照を確認した。[T030の87行](../T030/run-003/score.json) · [統合版の87行](../vision/run-001/machine-score.json) · [独立レビュー](run-001/independent.json) · [破損対照の追加レビュー](run-001/independent-final.json)

## 再実行

変更前 `9fcaa0d` のworktreeを `BASE_CHECKOUT` に指定する。新しい出力先でZIPを展開し、変更は別コピーに加える。

```sh
python3 validation/development/T039/verify.py --out /tmp/wcag-t039 --baseline BASE_CHECKOUT
```

T030と統合版の全収集runが手元にある場合は、それぞれ `--t030-run` と `--vision-run` に元のディレクトリーを指定して87行を比較する。採点結果は、探索台帳の登録と採取したファイルから確認できる範囲を示す。[ADR 0123](../../../docs/adr/0123-check-dialog-exit-score-evidence-hashes.md)
