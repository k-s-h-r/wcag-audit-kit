## 目指すのは、証拠に基づいて自律的に検証するスキル

Webサイト・Webアプリに対し、有償の専門的なWCAG検証に相当する品質を目指す。URL・対象範囲・必要なアクセス条件を受け取ったAIが、ページと操作状態を調べ、途中の人手なしに検査・判定・報告まで進める。検出漏れと誤判定を減らし、適合を説明できる証拠を揃えることが目的である。

段階的な開発の到達目標はWCAG 2.2 AAとする。まず指定の1ページで、機械的に判断できる観点の正確さを確かめる。既存のAAAの問題集も保持する。サイトの実装修正は別スコープとする。構成整理や帳票の拡張は、検証能力を改善するために必要な範囲で行う。

利用者はAI環境からスキルを呼び出す。利用先のAIが検査の計画、実操作、証拠の読み取り、判定、追加検査を担当する。Python等の補助コードは、測定・証拠保存・計算・採点・帳票作成を支える。利用者による毎回のCLI操作や、PythonへのLLM APIの組み込みを前提にしない。

検証対象にはページ全体、表示条件による変化、一連の手続きが含まれる。[WCAGの適合要件](https://www.w3.org/TR/WCAG22/#conformance-reqs)に沿って、確認した範囲と残った範囲を説明する。問題集の成功を、そのまま任意のサイトの適合保証には使わない。

## 機械で確認し、残る観点に必要な手段を使う

検証手段は、機械ルール・実入力・数値計測、AIによる画像や文章の意味判断、実スクリーンリーダーによる操作・発話の確認の順に整備する。AI環境からスキルを呼んだ場合でも、machineでは意味の判定をAIに委ねない。

実行時も、対象ページ・状態で可能な機械検査を先に行い、結果と残る確認を分ける。画像の代替文が存在するかは機械で確認し、画像の情報を伝えるかはAIで比較する。通知が実際に読み上げられるかは、対応する環境でスクリーンリーダーを操作して確かめる。実スクリーンリーダーは、より高性能なAIモデルだけでは代替できない。

AIや実スクリーンリーダーには、必要な対象・状態・証拠・未解決の観点を渡す。AIの探索で新しい状態が見つかったら、その状態にも機械検査を適用する。機械で結論が出た観点を重複して判定し続ける処理は減らし、追加の確認で解決した件数と費用を測る。

「機械でやり切る」は、選んだ範囲と実行条件で機械検査を実行し、失敗や未探索を含めて結果を記録することを指す。あらゆる機械検査の実装完了を、次の段階へ進む条件にはしない。安定した範囲を利用しながら、残る課題を別に改善する。

現在の[モード仕様](../skills/wcag-audit-kit/references/verification-modes.md)では、同じrunの途中でモードを変更できない。machineからai・full等へモードを変えて追加検証する場合は別runとする。最初からai又はfullを選んだrunでは、そのモードで使える手段を機械検査から順に適用できる。将来、別runの証拠を再利用する実装を加える際は、元run・対象・状態・環境・版の一致を確認し、追加結果の出所を追えるようにする。

## 1ページの機械検査を固め、対象範囲と検証手段を広げる

開発の順序を次のように定める。表の状態は、この計画に沿った評価・改善の進捗であり、既存実装の有無とは区別する。

| 段階 | 成果物と完了条件 | 状態 |
| --- | --- | --- |
| 1. 指定の1ページを機械で検査する | まず下記2観点の現状を測り、失敗原因を一つずつ直す。必要な取得照合も接続する。選んだ範囲で期待結果が一致し、誤検出・未確認が残らず、意味判断等の残作業を正しく報告できること | 画像・タイトル、メニューと開閉部品の24経路、コンボボックス等の18経路、宣言したiframeからの離脱を確認した |
| 2. 指定URL一覧を機械で検査する | 安定した1ページ検査を各URLへ適用する。URLごとの成功・失敗・未実施を一覧化し、ページ別結果と集計が一致すること。中断後も未完了の作業を再開できること | G2達成。`page-batch`の中断・再開と、専用MCPを使った隔離Codexからの実行を確認 |
| 3. URLを収集し、検証対象を一覧化する | 基準URLと範囲からリンクをたどり、利用可能なサイトマップ等と照合する。取得元・除外理由・未訪問を残し、既知のサイトで発見漏れを測る。採用した一覧を段階2へ渡せること | ローカルの認証後・操作後の候補を含む9 URLを実際のバッチへ引き継いだ |
| 4. 1ページの残る確認をAIで進める | 画像の意味、タイトルの主題、見た目からの操作候補等を、実際の証拠と比較する。選択範囲で正しく判定し、新しく発見した状態を機械検査へ戻せること。必要な証拠だけ渡した場合の費用も測る | タイトルの意味は正常例と問題例で根拠付きで確認。図は読み取りと数値照合を確認し、代替説明の適否は未達 |
| 5. 実スクリーンリーダーで確認する | 限定したOS・ブラウザー・支援技術の組み合わせで、操作と発話を取得する。正常例で環境を確認した上で、読み順・名前・状態通知等の選択範囲を検証できること | ChromiumとOrca 48.1・51.1で4.1.3の対照2組を実測。別々のrunで計4例が一致 |
| 6. サイト・アプリ全体の試験を組み立てる | 対象範囲と代表ページを選び、認証後・動的状態・一連の手続き・ページ間比較を検査する。各ページへ必要な手段を適用し、選定根拠・証拠・未確認範囲を含む報告を作れること | T014の別サイトで4ページを検査し、初回16観点、追加証拠を採点した結果は20観点が期待と一致 |

各段階で、基準値を記録する、失敗原因を直す、同じ条件と別の問題で確認する、という順に進める。基準値の記録は失敗を含んで完了できるが、選択範囲の検証能力を達成したとは扱わない。判定・取得の期待結果、対象と状態を実行前に固定し、成功した行だけを集計対象にしない。

段階2・3は、段階1で安定した範囲を使って進められる。AIや実スクリーンリーダーの完成を待たない。操作しないと見つからないURLや複雑な状態の探索は、段階4以降の能力を段階3へ追加する。既存の全問題集を保持し、以前の結果が悪化していないかも確かめる。

機械・AI・実スクリーンリーダーは、WCAGの適合レベルA・AA・AAAとは別の検証手段である。機械検査だけの段階でも限定した観点の正確さを実証できるが、1ページの全AA基準を通過したとは報告しない。

## サイト全体の試験は、URL一覧と選定根拠から組み立てる

評価事業者が行う試験の工程を組み立てる参考として、[WCAG-EM 2.0](https://www.w3.org/TR/2026/NOTE-wcag-em-2-20260723/)を使う。範囲の定義、対象の調査、代表的なサンプルの選定、検証、報告を成果物で追えるようにする。以下は今後の実装・評価項目であり、現在すべてを自動実行できるという意味ではない。

| 工程 | 残す成果物 |
| --- | --- |
| 試験範囲を定める | 基準URL、対象範囲、WCAGの版とレベル、認証・権限、対象環境、範囲を制限する理由 |
| サイトを調べる | URL台帳と取得元。ページ種別、共通部品、主要機能、利用技術、操作後の状態・経路、到達できなかった箇所 |
| 試験対象を選ぶ | 全件又は抽出の方針。代表ページと無作為抽出の記録、選定・除外理由、一連の手続きに必要なページと状態 |
| 検証する | URL・状態・環境・確認観点ごとの結果と証拠。機械で終えた部分、AI・実スクリーンリーダーへ渡す部分、未実施・判断保留 |
| 報告する | 試験範囲と対象URL一覧、判定根拠、再現手順、未確認範囲。HTML・JSON・Excelから元の証拠を追えること |

同じURLでも、権限や操作によって異なる画面になる場合は状態を別に管理する。小規模サイトで全件を扱う場合も、大規模サイトで抽出する場合も、取得候補と実際の試験対象を区別する。抽出したページの結果から、未検査のページを含むサイト全体への適合宣言は行わない。

## 成績は、見逃し・誤判定・自律性を分けて記録する

| 指標 | 記録する内容 |
| --- | --- |
| 見逃し | 既知の問題を検出できなかった件数。未確認と、誤って適合にした件数を分ける |
| 誤検出 | 正常な実装を問題として報告した件数 |
| 探索漏れ | 検査すべき対象・状態・操作経路を発見できなかった件数。指定された対象の試験とは分ける |
| 自律検証の範囲 | 正しく判定できた件数、未実施、判断保留、人への引き継ぎを、対象総数とともに示す |
| 再現性 | 同じ条件で再実行したときの判定と探索範囲の変化 |
| 費用と時間 | 機械・AI・実スクリーンリーダーの段階ごとの実行時間、追加で解決した件数、取得できる実使用トークン数とその範囲。取得不能な値は未取得と記す |

判定と取得の観点、モードによる省略は区別する。台帳件数、コマンドの終了成功、ユニットテストの成功をAIの検証精度に置き換えない。人への引き継ぎで作業を終えても、自律検証の成功には数えない。未実施・判断保留を適合へ変えず、原因を次の改善対象にする。

目標の品質へ近づいたと判断する数値基準、繰り返し回数、対応環境の範囲は、実測を得て具体化する。数値を先に満たしたように見せるため、採点対象や期待結果を緩めない。期待結果の誤りを直す必要が生じた場合は、根拠を別の変更で示し、旧runを保持して別の版・runで検証する。

## 新しいセッションへ引き継ぐとき

開発PRでは、担当タスクの状態、完了根拠、未確認事項、次の作業を担当ファイルへ記録する。この文書の段階と次の作業が変わる合流時は、同じPRで更新日、状態、完了の根拠となるPR・検証記録を更新する。セッションを中断する場合も、担当ファイルへ途中のrunと再開条件を記録し、完了扱いにしない。秘密情報は記載しない。

方針の変更は新しいADRで説明し、過去のADRを進捗欄として書き換えない。進捗はこの文書、判断の履歴はADR、実測は`validation/`から参照する記録として保つ。

対応するAI環境・ブラウザー・支援技術の組み合わせと、独立した専門家による問題集の正解確認は今後具体化する。開発時に評価の正確さを確かめることと、利用時に人の判断を必須にすることを分ける。

再開時の依頼例：

> AGENTS.md、docs/ROADMAP.md、docs/tasks/README.mdと担当タスクを読み、開始条件と現在の状態を確認して、未完了の作業を進めてください。変更は別worktreeと作業ブランチで行い、新しいADRと検証記録を添えてPRを作成してください。
