# 人手を介さないWCAG検証へ進める開発計画

更新日：2026-11-18。現状の確認対象：`007894b`（PR #9のマージ後）。

この文書を、開発方針・現在地・次の作業の参照先とする。新しいセッションでは[AGENTS.md](../AGENTS.md)とこの文書を読み、[次の作業](#次の作業)から再開する。判断の背景は[ADR 0017](adr/0017-autonomous-audit-development.md)に残す。

## 目指すのは、証拠に基づいて自律的に検証するスキル

Webサイト・Webアプリに対し、有償の専門的なWCAG検証に相当する品質を目指す。URL・対象範囲・必要なアクセス条件を受け取ったAIが、ページと操作状態を調べ、途中の人手なしに検査・判定・報告まで進める。検出漏れと誤判定を減らし、適合を説明できる証拠を揃えることが目的である。

最初の到達目標はWCAG 2.2 AAとし、既存のAAAの問題集も保持する。サイトの実装修正は別スコープとする。構成整理や帳票の拡張は、検証能力を改善するために必要な範囲で行う。

利用者はAI環境からスキルを呼び出す。利用先のAIが検査の計画、実操作、証拠の読み取り、判定、追加検査を担当する。Python等の補助コードは、測定・証拠保存・計算・採点・帳票作成を支える。利用者による毎回のCLI操作や、PythonへのLLM APIの組み込みを前提にしない。

検証対象にはページ全体、表示条件による変化、一連の手続きが含まれる。[WCAGの適合要件](https://www.w3.org/TR/WCAG22/#conformance-reqs)に沿って、確認した範囲と残った範囲を説明する。問題集の成功を、そのまま任意のサイトの適合保証には使わない。

## 現在は、問題集を使ってAIの能力を測る段階

| 揃っているもの | 現在の制約・次に確かめること |
| --- | --- |
| `skills/`の4スキルと単独配置の仕組み | 現在の単独検証の既定は`machine`。AIによる意味判断は既定では始まらない |
| 86基準・131観点、304ケース・312ページの問題集 | 入力の収録範囲であり、全件をAIが解けることを示す実績ではない |
| 証拠保存、判定の取り込み、独立した採点、比較、HTML・JSON・Excel出力 | 自動接続されている判定は限定的。取得の17観点・36期待結果の照合は未接続 |
| 検査担当に公開ページと作業票を渡す手順 | 作業票が基準・状態・対象を与える。URLだけから検査対象を発見する能力は別に評価する |
| 正解を公開ページから除く構成 | 同じリポジトリを読めるAIから、正解を物理的に隔離する仕組みは未整備 |

詳細は[問題集](../benchmarks/README.md)、[検査担当の手順](../benchmarks/WORKER.md)、[現在のスキル](../skills/wcag-page/SKILL.md)を参照する。上の数値は確認時点の値で、更新時は問題集の一覧と照合する。

限定した実証は既にある。[ACTの2ルール・12例](../validation/act-held-out/README.md)や[既知のサイトでの受入試験](../validation/site-acceptance/README.md)は、その対象と条件での記録として保持する。[旧問題集の実測](../validation/criterion-benchmarks/README.md)と[配置変更後の確認](../validation/skill-layout-main-integration/README.md)も参照できる。今回の文書追加では、新しいAI検証は実施していない。

## 開発は、基準値の記録から始める

| 段階 | 成果物と完了条件 | 状態 |
| --- | --- | --- |
| 1. 現行AIの実力を測る | 下記3基準を実際のスキル実行で検査し、証拠・採点・未確認・再実行手順を新しいrunへ残す。失敗を含めて評価を再現できること | 次に着手 |
| 2. 選んだ範囲を自律的に検証する | 取得結果の照合を接続し、探索漏れ・意味の誤判定・証拠不足等を一種類ずつ改善する。選択範囲の必要な期待結果が一致し、誤検出・未確認・人への引き継ぎが残らないことを確認する | 未着手 |
| 3. サイト・アプリの探索を評価する | URLと対象範囲から、複数ページ、入れ子、エラー、条件付き表示、一連の手続きを発見して検査する。改善に使っていない別の問題でも測る | 未着手 |
| 4. AAの範囲を広げる | 基準別の実証を増やし、必要な実スクリーンリーダー・表示環境・メディア等の検証を接続する。環境ごとの実績と残る制約を公開する | 未着手 |

段階1の完了は、現状を測れたことを意味する。段階2以降の検証能力の達成とは区別する。既存の全問題集を保持しながら、改善した範囲と既存結果の悪化を確かめる。手元の既知例で一致した後も、別の問題での評価と再実行時のばらつきの確認を続ける。

通常の依頼でAIが必要な検証方法を計画する動作へ、段階的に改善する。現在の`machine`既定やモードの制約は、この文書では変更しない。動作を変更するPRでは、既存利用との関係を新しいADRに記録する。

## 次の作業

次のPRは「3基準について、実際のAIによる検査と採点を再現し、基準値を残す」に絞る。

対象は1.1.1（非テキストコンテンツ）、2.1.1（キーボード）、2.1.2（キーボードトラップなし）。画像の意味判断と、動的な操作をともに調べる。現行の`ai`モードを明示して使う。実スクリーンリーダーや全AA基準の達成を、この試験で実証したことにしない。

1. 現在のブランチ・変更差分・関連PRと、この節の状態を確認する。未コミットの利用者の作業を保持し、作業ブランチと新しいADRを用意する。
2. [問題集の実行手順](../benchmarks/README.md)と[WORKER.md](../benchmarks/WORKER.md)を読み、選択範囲、モード、予算、実行環境を固定する。正常例と問題例の両方を含める。
3. 検査担当AIと採点担当を分ける。検査担当にはスキル・公開ページ・作業票・必要な生の証拠を渡し、正解ファイル・採点結果を文脈とファイルアクセスの両方から除く。正解を読んだ開発セッションを、そのまま検査担当にしない。分離できなければ、その制約を記録し、正解を伏せた評価の完了とはしない。
4. 新しいrunを作り、実際のAIが操作・観察・判定・結果の取り込みまで進める。実行したモデル、スキルと実装の版、ツール、環境、操作履歴、停止理由を記録する。対象サイトやケースIDから正解を埋め込む専用スクリプトを検証能力として数えない。
5. 採点側で正解と照合し、下記の指標を記録する。取得の観点は現行の手順どおり証拠を保存し、未接続の照合を成功扱いにしない。この段階では、必要な取得期待が残るため厳格採点が未完了になり得る。
6. 保存場所と再実行手順を`validation/`内の新しい記録から参照できるようにする。既存の記録・判定・原始証拠は上書きしない。PRに実行内容と未確認事項を書き、この文書の現在地と次の一手を更新する。

結果を見てから、次に直す原因を一つ選ぶ。最初の実測前に、スキル全体の書き直しや広範囲の検出器追加を始めない。

## 成績は、見逃し・誤判定・自律性を分けて記録する

| 指標 | 記録する内容 |
| --- | --- |
| 見逃し | 既知の問題を検出できなかった件数。未確認と、誤って適合にした件数を分ける |
| 誤検出 | 正常な実装を問題として報告した件数 |
| 探索漏れ | 検査すべき対象・状態・操作経路を発見できなかった件数。指定された対象の試験とは分ける |
| 自律検証の範囲 | 正しく判定できた件数、未実施、判断保留、人への引き継ぎを、対象総数とともに示す |
| 再現性 | 同じ条件で再実行したときの判定と探索範囲の変化 |
| 費用と時間 | 実行時間、取得できる実使用トークン数とその範囲。取得不能な値は未取得と記す |

判定と取得の観点、モードによる省略は区別する。台帳件数、コマンドの終了成功、ユニットテストの成功をAIの検証精度に置き換えない。人への引き継ぎで作業を終えても、自律検証の成功には数えない。未実施・判断保留を適合へ変えず、原因を次の改善対象にする。

目標の品質へ近づいたと判断する数値基準、繰り返し回数、対応環境の範囲は、実測を得て具体化する。数値を先に満たしたように見せるため、採点対象や期待結果を緩めない。期待結果の誤りを直す必要が生じた場合は、根拠を別の変更で示し、旧runを保持して別の版・runで検証する。

## 新しいセッションへ引き継ぐとき

開発PRでは、この文書の段階と次の作業が変わったかを確認する。変わった場合は、同じPRで更新日、状態、完了の根拠となるPR・検証記録、未確認事項、次に行う一つの作業を更新する。セッションを中断する場合も、途中のrunと再開条件を記録し、完了扱いにしない。秘密情報は記載しない。

方針の変更は新しいADRで説明し、過去のADRを進捗欄として書き換えない。進捗はこの文書、判断の履歴はADR、実測は`validation/`から参照する記録として保つ。

対応するAI環境・ブラウザー・支援技術の組み合わせと、独立した専門家による問題集の正解確認は今後具体化する。開発時に評価の正確さを確かめることと、利用時に人の判断を必須にすることを分ける。

再開時の依頼例：

> AGENTS.mdとdocs/ROADMAP.mdを読み、「次の作業」の現在の状態を確認して、未完了の作業を進めてください。変更は作業ブランチで行い、新しいADRと検証記録を添えてPRを作成してください。
