# WCAG検証の開発計画

更新日：2026-11-21。

[やりたいことメモ](VISION.md)を開発の出発点にする。URLからページや一連の手続きを見つけ、決めた範囲がWCAGに適合しているかを根拠付きで答える。そのために次に確かめることと、現在までの実証をここに記す。着手条件と引き継ぎは[タスク一覧](tasks/README.md)を参照する。

## 次の作業

個々のPRを一緒に使える作業ブランチで検証し、VISIONの項目ごとに操作と帳票の根拠を照合する。主な結果と再実行方法は統合検証にまとめる。採用された版で同じ試験を行う際にも、この条件を使う。[VISIONの統合検証](../validation/development/vision/README.md)

統合実証後は、URL起点で状態を観察できた行のうち判定がなかったものから確認する。T030では、2.1.2の12例のうちダイアログの正常例と問題例を両幅で区別した。複数のフォーカス先やフレームに残る離脱経路は、別の対照で続けて調べる。[T030の結果](tasks/T030-dialog-keyboard-trap.md)

初回実証の着手順と元の測定は次のとおり。

1. **キーを送った後の実行結果を確かめる。** [T020](tasks/T020-url-only-machine-score.md)でURLから76ページ・87行を測った。問題39行中、検出8、状態・経路の未確認11、到達後に判定なし20だった。数量変更ではクリック後とEnter後の値が異なっても、報告はキーの送出までだった。[T024](tasks/T024-keyboard-function-result.md)で、通常の入口からこの差を照合する。
2. **適合の結論を検査票に出せるか確かめる。** [T021](tasks/T021-scope-conformance-report.md)では、保存済みの判定と証拠を使い、対象とする範囲の適合・不適合・未確認を利用者に示す。T024と独立して始められる。

操作経路の残りは[T018](tasks/T018-widget-operation-sequences.md)、操作後の差分再検査は[T019](tasks/T019-post-operation-rechecks.md)に置く。T018のメニューとコンボボックスは検証済み。残るアコーディオンはURLから対照例をたどれるかを先に確認する。T019は全体再検査との一致を確認し、必要な検査を保ったまま再検査量を減らす。

次は[T022](tasks/T022-url-to-process-audit.md)で、URLを出発点に一つの手続きを見つけ、機械検査に残った判断をAIや必要な支援技術で確かめ、二つの成果物までつなぐ。この実証の操作記録を使い、[T023](tasks/T023-accessibility-review-pilot.md)でアクセシビリティ点検の結果を試す。着手の順序と並行できる範囲は[タスク一覧](tasks/README.md#次に着手する作業)に記す。

## URLから始まる検証を評価する

問題集には86基準・131観点、306ケース・314ページがある。収録範囲、操作条件付きの機械検査の成績、URLだけで探索した成績はそれぞれ記録する。条件付きの検査は、対象に到達した後の処理が正しいかを調べる回帰試験に使う。 [問題集の入口](../benchmarks/README.md)

- 採点側が対象行、問題と対照、期待結果を実行前に固定する。URL単独の評価では、検査側にページのURLと共通の実行条件を渡し、操作手順・個別設定・正解は採点側に置く。モデルを使う評価ではファイルアクセスも分ける。
- 経路の発見、対象への到達、実際の操作結果、判定と証拠を別に見る。見逃し、誤検出、未到達、到達後の判断保留、収集失敗を分け、正常例と未確認の行も分母に残す。
- 実装と問題集の版、使用した入力、環境、探索上限を記録する。変更前後を別runに保存する。必要に応じ、時間・費用と追加で解決した件数を比べる。
- 判定の記録と、実行・観察の証拠を採点する。報告の生成、CLIの終了、タスクの完了はそれぞれ記録し、WCAGの適合は達成基準と範囲の証拠から判定する。

## 検証に使う手段と受け渡し

できる範囲の機械検査を先に行う。残る観点は対象・状態・証拠を引き継ぎ、AIや実スクリーンリーダーで確かめる。例えば機械で代替文の存在を確認し、AIが画像の情報を伝えるか比較する。通知については、操作と実際の発話を対応付ける。新しい状態を見つけたら機械検査にも戻す。

AI環境から[4スキル](SKILL-DESIGN.md)を呼び出す。補助CLIは操作・測定・証拠保存・採点・帳票作成を支える。[検証手段の設定](../skills/wcag-audit-kit/references/verification-modes.md)を変更する場合は別runを使う。最初から `ai` や `full` のrunでは、その設定で使える手段を順に進める。別runの証拠を再利用できるようにする場合は、対象・状態・環境・版の一致を確かめ、証拠の出所を残す。

## サイトの試験範囲と結論

サイトの試験では、URL台帳と選定理由を残す。ページ全体、異なる表示や権限、必要な一連の手続き、アクセシビリティサポート、非干渉を確認する。代表ページの抽出を使う場合は、検査したページと未検査の範囲を明示する。適合の結論は、要件を確認した範囲に対して示す。 [適合要件](https://www.w3.org/TR/WCAG22/#conformance-reqs) · [試験の組み立て](https://www.w3.org/TR/2026/NOTE-wcag-em-2-20260723/)

共通部品の再利用は、同じ環境で一致した文字コントラストの証拠を参照できることまで確認した。ページごとの状態・表示・周辺の内容に差がある場合は、その差に応じて測り直す。修正前後はそれぞれの版で検査し、解消した箇所と新しい問題を比べる。[T013](tasks/T013-site-selection.md#共通部品の同じ初期表示の測定を参照) · [Issue #4](https://github.com/k-s-h-r/wcag-audit-kit/issues/4)

修正前後の比較は、同じ部品を使う6ページで確認した。検査結果や証拠を照合できないページも比較に残す。[T025の検証](../validation/development/T025/README.md)

操作の比較はローカルの対照から始める。本番での操作は対象サイトの権限、操作による副作用、通信条件を確かめて計画する。操作時の外部通信の隔離は[Issue #82](https://github.com/k-s-h-r/wcag-audit-kit/issues/82)で検討する。
