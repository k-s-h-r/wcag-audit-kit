# T004：Codexで明示呼び出しと作業範囲を確認する

状態：隔離したCodexで4スキルの本文展開、指定ページの機械検査、保存済み結果の報告、親から子手順を読んだ後の指定一覧の検査を確認した。モデルによる最終回答の正確さと時間は確認を継続する。

最初は利用中のCodexだけを対象に、4スキルの設定がホストでどう動くかを確かめる。設定ファイルを読む試験と、ホストがスキルを読み込む実際の動作を分ける。

## 作業と成果物

利用するCodexの版、配置先、配置したスキルの版、再読み込み方法、呼び出し方法を記録する。既存の利用者設定を保持し、独立した検証用の配置・セッションで確認する。実行環境や必要な権限が足りなければ、その不足を記録する。

新しいセッションで、明示したpageの読み込み、通常の開発相談から監査を始めないこと、1ページ依頼で巡回しないこと、報告だけで再検査・判定更新をしないこと、全体監査から子の手順を読めることを調べる。実ページを操作する範囲は小さなローカルfixtureに限定し、ホストの読み込み記録・操作履歴・通信や成果物から確認する。

成果物は`validation/development/T004/`の環境、各入力、実際に読み込まれた手順、操作・成果物、結果と制約。単にモデルへSKILL.mdを手で読ませた結果を、ホストの明示呼び出し成功には数えない。1回の結果を全バージョンでの動作保証にも広げない。

## 完了条件と確認

- 上記の各場面について、実測結果又は実行不能な理由がある。
- 自動呼び出しを抑制する設定と、明示起動後の内部手順の再利用を区別する。
- 確認したホスト・版・操作方法を、新しいセッションで再現できる。
- 失敗した場合は、ホスト側の制約かスキル指示の問題かを根拠付きで記録する。

ホストの制約が残る場合、T004の調査記録は完了できるが、その環境の呼び出し成功は未達として残す。

## 担当範囲と引き継ぎ

まず記録だけ作る。指示や設定の修正が必要なら、対象となるSKILL.md又はagents設定を特定し、調整担当へ知らせて小さな修正PRに分ける。共通ランタイム、採点器、他ホストの対応は広げない。

完了時に記載する情報：確認したCodexの版、配置と呼び出し方法、各場面の結果、実行不能条件、T011以降が使える環境。

## 元のユーザー環境での起動試行

4スキルの`allow_implicit_invocation: false`を確認し、独立した作業ディレクトリーの`.agents/skills/`に配置した。Codex CLI 0.167.0-alpha.4で`codex exec --ephemeral --json --skip-git-repo-check -s read-only -C <検証ディレクトリー>`を使い、`$wcag-page`の明示呼び出しを試した。アプリサーバーの初期化が読み取り専用ファイルシステムで停止し、終了コード1、JSONL出力は0行だった。実ホストのスキル選択や監査動作は未実施。次はセッションを初期化できる隔離環境で、単独の呼び出しから再試行する。

CLIのSQLiteとログを一時ディレクトリーに分けて再試行した。SQLiteは準備できたが、起動時に書き込みを要求する`installation_id`を現在のCodexホームに作れず、アプリサーバーは応答を返さなかった。実ホストの選択は保留のままとする。[Codex CLI 0.167.0-alpha.4の実装](https://github.com/openai/codex/blob/rust-v0.167.0-alpha.4/codex-rs/core/src/installation_id.rs#L17-L25)

## 隔離環境での発見と本文の展開

DockerのDebian 13で同じCodex CLI 0.167.0-alpha.4を起動した。`skills/list`で配置した4スキルを有効として取得し、エラーは0件だった。各試行を新しい一時セッションで開始し、通常の質問と4つの明示指定を比較した。通常の質問では4スキルの本文はモデルに渡らず、明示指定では選んだ1つだけが渡った。通常の `codex exec` に `$wcag-page` を渡す試行でも、モデル入力に本文を確認した。

入力はコンテナ内の受け口で取得した。1ページの巡回制限、報告時の再検査と判定更新の有無、親スキルから子の手順を使う動作は、試験を完了できるモデルで実行して確認する。G2のスキル実行、T011の正解を隔離したAI評価、T014の統合試験はこの確認の後に進める。[ADR 0046](../adr/0046-measure-codex-skill-dispatch-offline.md)

入力の確認は `python3 tests/codex_skill_dispatch.py` で再実行できる。既に取得したDebian 13 slimのDockerイメージ、Codex CLI、単独で動作するPythonランタイムを使う。実行すると、4スキルの発見、明示指定と通常入力、CLIからの指定を順に照合する。

## ローカルモデルによるツール読み取り

同じCodex CLIから、隔離したOllamaのQwen3-VL 2B Instructを使い、試験ファイルの内容を読むように依頼した。MCPの読み取りと値の照合は2回成功した。最終応答を待った150秒と90秒の試行は、両方とも時間切れだった。シェルではモデルが不正な引数を出し、シェルを無効にした試行でも、別のツールを要求して読み取り後の依頼を完了できなかった。確認できたのは、実モデルから専用の読み取りツールを実行して値を受け取るところ。認証済みの接続又は、必要な操作を完了できるローカルモデルを使って、ページ検査・報告を試す。[ADR 0049](../adr/0049-bound-local-model-tool-preflight.md)

## 固定したローカルページでの検査と報告

Codex CLI 0.167.0-alpha.4、Ollama 0.40.16、Qwen3-VL 4B Instruct、Chromium 156.0.8078.79を使用した。モデル配布のマニフェストはSHA-256 `84f7ed8042fa7cdbd902f7dcb7d0370e032095047cc3244179f263b77b5bc318`。Debian 13の隔離環境で外部ネットワークを切り、配布用スキルを作業先の`.agents/skills/`に配置した。各入力は新しい一時セッションへ渡した。実行には`codex exec --oss --local-provider ollama -m qwen3-vl:4b-instruct --ephemeral --ignore-user-config --json -s read-only`を使い、`model_provider="ollama"`と`model_reasoning_effort="none"`を指定した。

専用のMCPツールに固定したURLと一時runだけを許可した。単独検査は`page-audit --url <対象> --out <新しいrun> --mode machine --max-states 4 --max-steps 12 --max-depth 2`、報告は同じrunへ`page-report --run <run> --page-exact <対象>`を実行した。対象ページには代替文のない画像と対象外のページへのリンクを置いた。親手順の試験では実際に配置した子の`SKILL.md`を読むツールと、2件の確定URLだけで`page-batch`を実行するツールを提示した。モデルには利用できる試験ツールを短い追加指示で案内した。通常のシェルを通じた運用は別途確認が必要。
