# T020 URLだけで機械検出対象の全87行を測る

状態は未着手。前提は[T017](T017-url-only-exploration.md)の限定測定と、[T009](T009-machine-gap.md)で使った機械検出対象の問題集。どちらも利用できる。関連は[T018](T018-widget-operation-sequences.md)と[T019](T019-post-operation-rechecks.md)。

利用者がURLを渡したときに、`wcag-page` が既知の問題をどれだけ自力で発見し、根拠付きで報告できるかを測る。T017は8ページの測定で、[コンボボックス改善後の簡易探索](T018-widget-operation-sequences.md#コンボボックスの展開選択取消)は表示幅と操作別の照合24件中16件が期待と一致した。今回の成果物は、同じURL単独の条件を機械検出対象の全行に適用した基準値と、見逃しの内訳。基準値を取った後の検出器の改善は、原因ごとに後続作業へ渡す。 [計画した採点指標](../adr/0084-score-machine-findings-from-url-only.md)

## 作業と成果物

### 測定の対象と入力を固定する

1. 採点側で、`benchmarks/cases/` の `evidence_kind: program` かつ `modes.machine: evaluate` の判定行を列挙する。計画時点では76ページ・87行。内訳は問題39行、正常47行、対象外1行。計画の起点は `dc43bfe`。問題集の版と対象行一覧を保存し、結果が出る前に分母を固定する。 [機械検出対象の定義](../../benchmarks/README.md#間違いごとに必要な検査手段を確認する)
2. 本番と同じ `wcag-page` のページ検査に、公開ページのURLと全ページ共通の実行オプションだけを渡す。主測定は初期画面の収集後に同じrunで既定の簡易探索を行う。共通の設定は機械モード、レベルAAA、既定のPC幅とスマホ相当幅。AAAの問題4行も対象に含むためレベルAAAを使う。記録には実際のCLI、表示幅、上限、ブラウザー、検査実装のコミットを含める。 [通常の1ページ検査手順](../../skills/wcag-page/references/page-audit.md#初期画面の結果を先に返す)
3. 公開ページと素材だけを配信する。基準・観点、操作手順、対象セレクター、状態指定、期待結果、ケース専用の `probe` は採点側に置く。採点は探索終了後の保存済み帳票と証拠を読む。採点のための追加操作や条件付き計測は、主測定と別のrunにする。

### 問題の発見と、止まった段階を分けて採点する

- 主成績は**正しく検出した問題行数 ÷ 対象の全問題行数**。計画時の分母は39。該当ページ・対象・観点・状態・必要な入力経路に合う問題の指摘が、収集時の出力にあり、証拠を追える行を検出とする。原始証拠に差が記録されていても、採点側の後付け判断は検出数に含めない。
- 問題行は「検出」「誤って通過・対象外」「状態・経路の未確認」「到達したが判定保留・出力なし」「収集失敗・未実施」に分ける。対象を見つけたか、入力を送れたか、機能の結果を観察したかも、証拠があるところまで記録する。判定を一意に照合できなければ、その理由と証拠を残す。
- 対照48行は、期待との一致・誤検出・未確認に分ける。採点対象へ対応付けられない指摘は別に示し、個別に確認する。ページ・状態・表示幅別の証拠を保持し、主成績は問題集の採点行ごとに1回だけ数える。幅や入力方法を明示した期待行はその条件に従う。試験の上限、利用できない環境、送信等の制約で確認できなかった行も分母に残す。

成果物は、再実行できる収集・採点手順、全87行の採点データ、件数と代表的な見逃しを説明する読みやすい集計。入力・実装の版、再現コマンド、実測の根拠、未確認事項を `validation/development/T020/README.md` に記録し、実行ごとの帳票・操作ログ・計測証拠は別runに保存する。

## 完了条件と確認

- 対象一覧と集計が一致し、問題39行・対照48行のすべてに結果または未確認の理由がある。異なる版で対象が変わった場合は、元の内訳との差分と測定前に固定した分母を説明できる。
- 実行ログから、検査側へ渡したのがページのURLと共通設定だったと確認できる。採点結果から「どの出力が、どの期待行と対応したか」を検証できる。
- 検出成功、経路未確認、到達しても判定が出ない例、対照の誤検出または収集失敗を採点器で区別できることを確かめる。例えば[数量変更の問題例](../../benchmarks/cases/2.1.1/README.md#元の代表例操作例)では、Enterの送出だけで機能を実行できたとは採点しない。
- 集計と失敗原因をPRに示す。低い成績や未確認が残った場合も、全行の内訳と証拠が揃えば測定作業は完了できる。一般サイトへの適用結果は、この問題集での基準値と区別する。

## 担当範囲と引き継ぎ

着手可能。実行担当は `codex/t020-url-only-machine-score` などの別ブランチ・worktreeを使い、対象にする実装コミットを固定する。担当は `benchmarks/url_only.py` 周辺の収集・採点、必要な試験、このタスクと検証記録。共通の採点器やCLIに変更が必要になった場合は担当範囲を調整する。

本番の探索・判定コード、既存の問題集・期待結果・原始証拠を編集する作業は後続に渡す。T018・T019の完了を待たずに着手できる。並行する場合は実装版、ポート、ブラウザープロファイル、出力先を分ける。

測定後は、未到達の経路、条件が揃っても判定が出ない観点、誤検出を件数と再現証拠で示し、影響の大きい改善候補を渡す。中断した場合は、完了したURL、途中のrun、残件、再開条件をこのファイルに残す。
