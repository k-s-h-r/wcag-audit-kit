# T022 URLを起点に一つの手続きを見つけて報告する

状態：T021とT024の変更を含む依存ブランチでローカル実証を実施。前提は[T020の基準値](T020-url-only-machine-score.md)、[T021の報告](T021-scope-conformance-report.md)、[T011〜T014の限定実証](README.md#タスク一覧と開始条件)。

[T014](T014-site-acceptance.md)では選定サイトの機械検査、意味比較、実Orcaを組み合わせた。次は[照合した20観点](T014-site-acceptance.md#別サイトの受入試験)の実績を土台に、検査担当がURLから手続きの入口と状態を見つけ、必要な証拠をそろえて二つの成果物へつなげられるかを測る。 [VISIONの利用場面](../VISION.md#人が使うように最初から最後まで試したい)

## 作業と成果物

1. T020で残った経路や判断から一つを選ぶ。入口・操作後の状態・手続きの結果がある小さなローカルサイトで、標準HTMLで動く正常例と同じ外見の問題例を用意する。候補を選ぶ実験や修正に使ったケースは記録し、評価用の対照は別に持つ。
2. 検査側には起点URL、対象範囲、共通の操作条件だけを渡す。経路、セレクター、正解、採点結果は検査側の文脈とファイルアクセスから外す。機械だけの結果を先に記録し、AIを使う検査では画面から次に試す操作を選び、新しい状態に機械検査を適用する。発話を評価する観点は、正常対照で動作を確認した実スクリーンリーダーで操作と発話を採る。
3. 手続きのどこまで到達したか、何で判定したかを採点する。T021の未対応箇所一覧と検査票に、発見した状態と達成基準、根拠、適合の結論に残る確認を結び付ける。独立した実行を比較する場合は、それぞれのrunで報告する。

成果物は、固定した入力と採点、実操作と判断の記録、二つの報告、追加検査で解決した観点の内訳。文書は `validation/development/T022/README.md` に置き、試行ごとの原始証拠は別runに保存する。

## 完了条件と確認

- 入口、途中の状態、手続きの結果のうち、到達できた箇所と残る箇所を操作ログから追える。最終状態への到達と各観点の適否を区別できる。
- 同じ採点行で、機械だけの結果と追加検査後の結果を比較できる。正常例の誤検出、検出できた問題、未到達、到達しても未確認を分ける。
- 調べた範囲と根拠が二つの成果物にそろう。検査条件、対象外、未確認、実行した手段を残し、選んだ観点の成績と全体の適合の結論を区別する。

## 担当範囲と引き継ぎ

手続き一つの評価を担当する。検出器・採点器・帳票に修正が必要な場合は、再現条件を担当タスクへ渡す。モデルの版、使った手段と実行時間、取得できる費用、必要に応じて実スクリーンリーダーの版と操作環境を記録する。

状態・操作・つまずきの証拠がそろった経路を[T023](T023-accessibility-review-pilot.md)へ渡す。そろわなければ残りの取得条件を記録する。

## 実証と引き継ぎ

`codex/t022-url-to-process-audit` はT021のPRを起点とし、T024の探索実装を取り込んだ。作業先とrunを分け、Chromiumで工作室の見学予約を正常例と問題例で照合した。機械の先行検査では6項目中1件、別のCodexエージェントによる実操作後は6件が事前の期待と一致した。問題例の2.1.1と2.5.3は、不適合箇所一覧と検査票から根拠まで追える。発話と実サイトでの運用は今回の試験範囲外。次はT023で同じ経路の改善を実測する。[ADR 0098](../adr/0098-verify-a-process-from-its-entry-url.md) · [検証記録](../../validation/development/T022/README.md)
