# 0010 検証手段をモードで選び、確認観点ごとの対応表を共有する

日付：2026-11-16 / 状態：Proposed

## 背景

[ADR 0009](0009-readable-verification-observations.md)で全86基準を確認観点ごとに説明したが、利用者が機械のみ・AI併用・実スクリーンリーダー等を選ぶ設定と、そのモードで何が確認できるかを比較する表がなかった。従来のprofileは画像の深さとSRの要求を組み合わせたもので、検証手段の選択を表すには不足していた。

## 決定

machine、ai、screen-reader、fullの4モードを用意する。すべて機械検査を土台とし、AIによる内容判断と実SRの使用を独立して選ぶ。CLIと設定ファイルのverification.modeで指定し、設定なしの新しいpage-auditはmachineとする。旧設定・旧runにはモードを後付けしない。

モードの既定の画像・実SR設定を用意し、画像の深さと上限は既存のinspectionで調整する。明示した設定がモードの能力と矛盾する場合は停止する。再開は保存済みモードを維持し、変更は別のrunに記録する。

131確認観点の対応をversion付きJSONで管理し、READMEの○・△・×表と詳しい処理・準備の説明を生成する。○は当該観点に検査手段があること、△は一部の検査・証拠取得まで、×はそのモードでは確認しない又は信頼できる手段が不足することを表す。対象ページの合否・実施済みを表す記号にはしない。全86基準の観点を保持し、モードで省く観点をWCAGの対象外に変更しない。

新しいrunでは確認観点の定義とハッシュをverification.snapshot.jsonへ固定する。page-nextには選択モードで進める観点と、省く観点・理由を含める。AIを使わないモードへAIの判断指示を返さない。HTML・JSON・Excelに対応表と選択モードを示し、実SRの実施状態は保存された実際の観察から区別する。

CLIは機械探索・検査・証拠取得を実行し、AIサービスへ接続せず実SRも起動しない。AIの比較・実SRの対象専用シナリオは、許可されたモードでスキルと既存アダプターが実行する。モードの選択だけで実施済みにしない。実行者がAIか人かを既存台帳だけで技術的に証明できるとは表明しない。

## 代替案

- profileの名前変更だけでは、AIの内容判断と実SRを独立に選べない。
- 機械・AI・SRを排他的な3種類にすると、機械検査と他の手段を組み合わせづらい。
- READMEだけの対応表では、実行時の案内・帳票と別々に更新される。
- モードで確認しない基準を計画から削ると、未確認がなくなったように見え、適合や検証完了を誤って広げる。

## 影響

packageと4スキルを0.7.0に更新する。モード用の定義・スナップショット・帳票シートが増える。WCAGの検査定義、保存済みの判定と原始証拠、Excelの作業用交換形式は変更しない。旧runの読み取りは従来どおり維持する。手段の対応状況が変わった場合は定義と生成文書を更新する。

## 検証方法

代替文の存在と意味の比較、実SRが必要な観点、すべてのモードで未確認が残る観点を対照例にする。モードと観察設定の矛盾、途中のモード変更、スナップショット改変を拒否し、旧runの再解釈や未実施の適合化が起きないことを確認する。選択モードが作業指示・HTML・JSON・Excelで一致すること、実SRを選んでも発話の記録なしでは未実施であることを検証する。全Python試験、実ブラウザーでの各モードの収集・帳票、配布時の同梱、表・リンクの整合性を確認する。
