# 0025 公開Shadow DOM内の実フォーカスをキーボード検査で照合する

日付：2026-11-19 / 状態：Proposed

## 背景

[ADR 0024](0024-check-keyboard-path-outcomes.md)の指定経路を開閉部品へ適用した。2.1.1のp06とp07は、Tabで内側の部品へ到達した時点で両方とも失敗した。検査で使っていた`document.activeElement`は外側のホストを示すため、実際の操作を確かめる前に経路が終了していた。

## 決定

指定キー操作では、公開されているShadow DOMの`activeElement`を内側までたどり、照合と証拠に同じフォーカス先を使う。証拠と帳票には、識別できるホストと内側の操作対象を記録する。条件にホストを指定した場合も、実際に内側へフォーカスが移っていれば条件不一致とする。通常の収集で記録する文書のフォーカスは従来の形式で取得する。

## 代替案と影響

ホストと内部要素を同じフォーカス先とみなすと、ホストだけにフォーカスがある場合や別の内部要素への移動を区別できない。到達条件の比較は実際のフォーカス先に限定する。閉じたShadow DOMとiframe内部のフォーカスは追加検査に残る。保存した証拠を再判定するときは新しいrunを使う。

## 検証方法

`python3 tests/keyboard_checks_browser.py --out <新しい出力先>`で、3階層メニュー12経路と開閉部品12経路をChromiumで確認する。今回追加した7ページでは正常7経路が通過し、問題5経路を指定した位置で検出した。Shadow DOMの問題例では焦点到達の次のEnter・Spaceで開かないこと、入れ子のダイアログでは閉じられないことと閉じたあとのフォーカス移動が異なることを確かめた。ホストのみを期待した対照経路も不一致となり、HTML・Excelの対象・操作・証拠がJSONと対応した。Pythonの218テストを実行した。実行出力は作業ディレクトリーに保存する。
