# 0003 利用目的ごとのスキルと観察範囲の設定

日付：2026-11-15 / 状態：Proposed

## 背景

利用者は、開発中の1ページの確認と、サイト全体の検証を同じ仕組みで行いたい。従来の入口はサイト全体を前提にしており、URLの選定、ページの操作調査、判定、報告を1つの説明にまとめていた。クリック可能なdiv等を見つけるには、画面上の操作対象から調べる手順が必要である。費用に応じて画像や実スクリーンリーダーの確認を選べる必要もある。

## 決定

入口を4つに分ける。wcag-pagesは検査対象URLの選定、wcag-pageは1ページの操作・状態の調査と基準ごとの検査、wcag-reportは既存台帳の集計、wcag-audit-kitは依頼の振り分けと全体進行を担当する。基準本文・検査手順・実行コードは共通の原本から供給する。

サイト検証は1つのrunを正本にする。ページ検証スキルは、単独なら1ページのrunを作り、全体進行から呼ばれたら共通runの指定ページだけを検査する。ページ別の担当と再開には既存のタスクを使う。独立したrunの結果を暗黙に合算してサイト適合を宣言しない。

URL選定にはdiscoverとconfiguredを用意する。configuredは指定一覧だけを対象にし、リンク先を追わない。ページ検証の単独入口もconfiguredを使う。抽出の出力は候補一覧であり、サイト全体を発見した証明ではない。

ページ検証は実画面から操作候補を探す。見た目・ラベル・位置を画像へ結び付け、開く・内部を操作する・閉じる等の状態を記録する。DOMとアクセシビリティツリーは対象の特定と動作確認を補助する。イベントリスナーの列挙だけで操作対象を決めない。画像の保存だけで観察済みとは扱わない。

観察はquick、standard、thoroughと個別設定で選ぶ。画像はoff / states / all、実スクリーンリーダーはoff / optional / required。画像数に上限を設ける。これは作業量の設定であり、AIサービスの実トークン数や費用の保証ではない。スクリーンリーダーのrequiredは実施の依頼であり、収集器を動かしただけで実施済みにはならない。

新しいページ検証では操作・状態の調査票を保存する。省略、未探索、画像上限、未実施の必要な読み上げ確認を報告に残す。範囲が未確認なら検証完了にせず、具体的な残作業を引き継ぐ。旧runの定義・判定・証拠は保持する。

## 代替案

- 同じ巨大なSKILL.mdに入口だけ追加すると、1ページ利用でも全体の手順を読み込む必要がある。
- スキルごとに原典と判定方式を別々に管理すると、基準の版と結果の意味がずれる。
- UIを無差別にクリックすると、状態の網羅を示せず、送信や削除等を意図せず実行する。操作対象、実行する経路、テスト環境を確認してから操作する。

## 影響

各入口は必要な資料だけを読む。単体で導入できる配布用ディレクトリーを共通原本から生成し、全検証記録を各スキルへ複製しない。実証資料はGitチェックアウトのコミットを参照する。Git情報がない場合は明示した参照版を使い、省略時のmain参照も配布メタデータへ残す。

初期収集と基準の検査は別の段階である。ページ検証のスキルは収集後に実際の画像を読み、操作し、判定を記録する。CLIの収集成功だけを「1ページの検証完了」と表示しない。画面・操作・読み上げが省略された結果は、同じ範囲を検証した結果として比較しない。

## 検証方法

指定URLだけの訪問、抽出の別出力、画像モードと上限、未実施の観察の表示、操作調査票の証拠・残作業、旧runの読み取りを試験する。実ブラウザーの試験ページで、見た目がボタンでもdivで実装された操作と、開いた後の状態を画像・キー操作で確認する。4つの配布用スキルを新しいディレクトリーへ生成し、各入口・共通コード・参照先を確認する。
