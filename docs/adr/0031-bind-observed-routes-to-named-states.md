# 0031 公開された経路と到達条件で名前付き状態を確認する

日付：2026-11-18 / 状態：Proposed

## 背景

T017で操作後のimage-alt証拠を取得できても、採点器が初期状態だけを読むため2行が未確認だった。全非初期ノードを同じ状態にすると、繰り返し操作で画像を増やした別状態や異なる経路が混ざる。

## 決定

公開状態へ既存のactions・assertの書式を使って操作経路とselector・count・visibleの条件を与える。exploration_labelsは実際に探索した経路をラベル付けするだけで、新しい操作の実行や送信保留の解除には使わない。経路と実観測が一致した証拠だけを採点の状態へ対応させる。同じ見た目を別の経路で先に取得していても、指定経路の証拠を別に残す。

操作ヒントだけの旧状態や未ラベルの過去証拠は、自動で名前を推定せず未確認にする。条件不一致・遷移失敗・制限通信は対応させない。矛盾する同じ状態・対象の証拠は判断保留にする。取得照合は未接続のまま別に保持する。

1.1.1の入力版を4から5へ進め、2例の公開状態にだけ経路と到達条件を追加する。入力HTML・素材・全期待判定は不変と照合する。corpus digestは変わるためT001の元の計画と旧runを変更せず、新しい測定条件を別ファイルへ保存する。

## 代替案

単一の状態名があるからと全ノードをその状態へ割り当てる案、ケースIDから正解を作る案、旧runの未確認を新しいラベルで通過へ変える案は採用しない。状態を指定することと自力で全状態を発見する能力の評価は分ける。

## 影響

固定10行の操作後の判定も実際の証拠で説明できる。新しい公開状態の契約と実装の版を含む限定評価であり、任意のページ・全AA・未接続取得の完了は意味しない。main採用と提案版での能力確認を区別する。

## 検証方法

経路・条件の不一致、古い証拠、制限された遷移、矛盾する証拠を単体試験にし、実ブラウザーで同じ見た目の別経路を混ぜず、ラベルで送信保留を解除しないことを確認する。元の正解と公開ファイルの不変を照合し、新規runで固定10行を各2回測る。レビュー修正後の実装でも測り直し、残る省略・未確認とPR採用待ちを報告する。
