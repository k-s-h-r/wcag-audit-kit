# 0060 横並びタブの左右キー操作と選択前の状態を探索する

日付：2026-11-19 / 状態：Proposed

## 背景

自動探索のタブ向けキー候補に左右キーがなく、横並びタブにキーボードで入ってから表示される状態を検査できなかった。手動選択のタブでは、左右キーでフォーカスが移っても、EnterやSpaceを押すまで選択と表示は変わらない。[Issue #4](https://github.com/k-s-h-r/wcag-audit-kit/issues/4) [WAI-ARIA APGのTabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

## 決定

主文書または公開Shadow DOM内で、`role="tablist"` の子孫にある `role="tab"` を対象にする。向きが横、または向きの指定がないタブリストでは、Tabで到達する候補と現在フォーカスがある候補へ左右キーを送る。フォーカス先も状態の識別に使い、選択や表示が変わる前の状態からもEnter・Spaceを試す。

フォーカスがない `tabindex="-1"` のタブへのキー操作は、別のキーでフォーカスが移った状態から試す。再生時にその移動を確認できなければ、後続操作を未確認として記録する。左右キー後のフォーカス、`aria-selected`、表示中のパネルを操作と状態の証拠から追えるようにする。

## 代替案と影響

すべての部品に左右キーを追加すると、タブ以外でも試す操作が増える。向きと役割から候補を絞り、既存の探索上限を使う。DOMの選択と表示だけで状態をまとめると、手動選択の次の入力が失われる。状態の識別に使うフォーカスは横並びタブのものに限る。入力の送出とパネルの検査を記録し、キーボード操作全体の適否は検査票で確認する。

## 検証方法

`python3 tests/horizontal_tabs_browser.py --out <新しい出力先>` を実行する。左右キーで開くパネル、Spaceで開く手動選択のパネル、クリックでのみ切り替わる対照を比較する。縦並びの対照では左右キーを候補にしないことを確認する。信頼済み入力イベント、キー後のフォーカス、選択・表示、パネル内の画像に対する機械検査、ページ別HTML・JSON・Excelを照合する。修正前の実装では、同じ試験を `--baseline` 付きで実行する。
