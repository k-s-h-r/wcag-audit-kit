# 0059 実Tab後のフォーカス枠と隣接色を測る

日付：2026-11-19 / 状態：Proposed

## 背景

同じ部品でも、背景色によってフォーカス枠の読み取りやすさが変わる。既存の外枠測定は初期表示で実行し、2.4.7の画像証拠はキー入力前後の画面を保存する。操作中に現れる枠を隣接色と比較する機械検査が必要だった。[Issue #59](https://github.com/k-s-h-r/wcag-audit-kit/issues/59)

## 決定

`keyboard_checks`で1.4.11を指定し、最後のTab又はShift+Tabに`focus_contrast: true`を付ける。入力が主文書に届き、同じ対象が `:focus-visible` になって枠の宣言が変化したことを照合する。対象はサイトが指定した、不透明な単色の直線`outline`とする。角を除いた四辺の画素を確認し、外側の隣接色が単色なら3:1と比較する。経路ごとに初期表示から操作し、同じ対象でも背景ごとに観察する。[W3C Understanding 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

## 代替案と影響

CSSの値だけで算出すると、合成後の色や近くの別の描画を見落とす。ページ全体の画像を保存する方法では測定に無関係な表示も残る。明示した経路に限って枠周辺のPNGを保存し、従来の外枠測定と同じ画素比較を使う。複数の隣接色、丸い角、内側の枠、影、重なり、対象又は表示状態が確定できない場合は保留する。画像・観察条件・測定結果は実行の証拠に記録し、達成基準全体の判断は検査票に残す。

## 検証方法

`python3 tests/focus_outline_contrast_browser.py --out <新しい出力先>`を実行する。機械モードで同じボタンに実Tabで到達し、白い背景の21:1と暗い背景の約1.32:1を区別する。背景が複数色、常時表示の枠、Tabで届かない例は保留になることを確認する。HTML・Excel・JSONと、採取したPNGおよび実キーの記録を照合する。
