# 0020 開発計画を、依存関係と担当範囲を持つ並行作業へ分解する

日付：2026-11-18 / 状態：Proposed

## 背景

PR #11で[開発計画](../ROADMAP.md)と[スキルの設計](../SKILL-DESIGN.md)がmainへ入った。次は実測を進める段階だが、各セッションが同じコード・run・操作環境を共有すると、変更と証拠が混在する。段階的な開発を維持しながら、独立した作業を並行できる単位が必要である。

## 決定

[開発タスク](../tasks/README.md)に依存関係、担当範囲、成果物、完了条件と引き継ぎ事項を持つタスクを置く。最初は共通測定計画、Codexの呼び出し、対象固有の操作手順、URL一覧化の評価を並行する。計画の確定後、タイトルと画像の機械検査の基準値を別担当で測る。

測定と修正を分け、最初の実装・問題集を固定した成績を保持する。採点、報告、収集器の修正はファイルの担当を分け、共有箇所を変更するときは編集前に調整する。機械検査の選択範囲を次へ使える条件G1と、指定URL一覧へ適用できる条件G2を合流時に確認する。

作業ごとに別worktree・ブランチ・新しいrun・操作環境を使う。共通リソースの編集元と同期方式は維持する。各タスクファイルを進捗の参照先とし、段階や次の作業が変わる合流時に調整担当がロードマップを更新する。ADR番号は着手時に調整し、重複時は未マージの新規記録だけを改番する。

今回の変更はタスク分解と案内の保存に限る。タスクの実装・実測、AIエージェントや新しいチャットの起動は含めない。

## 代替案

ロードマップの段階をそのまま大きなタスクにすると、1ページ検査の中でも担当箇所が重なる。基準ごとの検出器追加だけを並行すると、測定条件や環境・報告の不備を見分けにくい。先に汎用のジョブ基盤や新しいデータ形式を作る方法は、実測前に実装範囲が広がるため採用しない。

## 影響

新しいセッションへタスクIDを渡して作業できる。担当が異なる状態・証拠を扱っても、起点と完了根拠を追える。共有するコード・GUI・ADR番号には調整が必要になる。後半のタスクは現在の前提に基づく分解であり、実測に応じて小さな子タスクへ更新する。

過去のADR、問題集の期待結果、保存済み判定・原始証拠は変更しない。タスク完了とWCAG検証の完了、基準値の記録と能力達成を区別する。

## 検証方法

14タスクの参照先、前提IDの存在、依存関係に循環がないこと、最初に4作業へ着手できることを確認する。各タスクに状態・成果物・完了条件・担当範囲・引き継ぎ事項があることを確認する。文書リンク・ADR番号・必須項目・差分を検査し、ロードマップの順序と現行CLI・runの制約に矛盾しないか読む。実検証の成績は各タスクへ残す。
