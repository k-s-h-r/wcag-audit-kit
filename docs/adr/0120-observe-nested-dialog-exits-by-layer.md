# 0120 入れ子のダイアログで閉じた層を観察する

状態は提案。

## 背景

通常のURL探索は、問題集045・046で親をクリックし、子をクリックまたはEnterで開いた。両例の補助Tabが子の内部を循環し、046では閉じるボタンにも届いた。子を開いた後のEscapeは24ステップ終了時の待ち行列に残り、2.1.2の両行は未判定だった。[通常探索と明示操作の比較](../../validation/development/T036/README.md)

T030の既存の観察には、閉じる前のモーダルが一つで、離脱後にはモーダルがすべて閉じているという条件がある。追加のキー試行は同じ一つの入力欄にとどまる対照を対象とする。したがって、入れ子の親を残して子だけを閉じる結果や、二つの入力欄を循環する結果は別の観察が必要になる。[T030](../tasks/T030-dialog-keyboard-trap.md)

## 決定

今回の作業では、通常探索の結果と、別runで明示したブラウザーの実入力を記録する。明示操作では、親子をどちらもキーで開いてから、どの層が閉じ、フォーカスがどの層のどの要素へ動いたかを記録する。復帰先の観察を、離脱できたことや2.4.3の適否と個別に扱う。

次の製品変更は、同じ主文書に親子一組を一意に特定できる経路で、子だけが閉じたことを観察するところから始める。操作前に親と子の要素を特定し、実入力後に同じ親が表示され、同じ子が閉じたことと、フォーカスが子の外へ移ったことを照合する。復帰先の要素と属する層は別の項目に記録する。別のダイアログが開く場合、親も閉じる場合、文書や対象が変わる場合は照合を保留する。

## 代替案と影響

探索の優先度を上げるとEscapeの経路は実行しやすくなるが、閉じた層を特定する条件は別に必要になる。先に明示したキー経路で子の離脱を確認し、実測をもとに通常の探索順を検討する。二つの入力欄の循環は、Escapeを含む試行の記録として扱う。循環からの自動判定には、他の離脱手段や案内の確認が必要になる。

## 検証

最初の製品変更は、046で実Escapeを送ると子が閉じ、親が表示されたままになることを両画面幅で確かめる。045でEscape後も子が表示される対照、および親も閉じる操作や別のダイアログが開く対照と区別する。既存の一層の観察と、通常24ステップの既存経路を追加実装時の回帰試験に使う。[操作記録と再実行方法](../../validation/development/T036/README.md)
