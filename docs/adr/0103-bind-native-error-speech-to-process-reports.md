# 0103 入力エラーの実発話を手続きの検査票に結び付ける

状態　Proposed

## 背景

T022では工作室の見学予約を起点URLから操作し、キーボードでの到達とアクセシブルな名前を検査票に反映した。入力エラーが読み上げられるかは、T012で実Orcaを使って確かめた通知の比較を、予約手続きに広げて検証する。

## 決定

同じ操作で同じ入力エラーを表示する予約サイトを2例用意する。事前に固定した実キー操作で、開始リンク、1名の入力によるエラー、2名への修正、確認画面をたどる。画面とフォーカス、操作後3秒の発話を照合する。両例で確認ボタン名の発話が得られ、同じ環境の正常例で通知が発話された場合に、問題例の通知を判定する。

入力エラーは確認ボタンにフォーカスが残るステータスメッセージとしてWCAG 2.2の4.1.3を調べる。入力欄に戻った際の説明と、エラー発生時にユーザーに届いた通知を時刻で区別する。検査票には両例の判定と証拠を保存し、確定した不適合は再現手順とともに不適合箇所一覧に載せる。

## 代替案

4.1.3の単独ページだけを繰り返すと、環境の発話は確認できるものの、起点から入力エラーを直して確認に進む手続きは測れない。通常のブラウザー操作やアクセシビリティツリーは画面とロールの証拠として使い、発話には専用X11とD-Busで起動したOrcaの原始ログを使う。

## 影響と検証

元のT022の対象・採点・証拠を保持する。T026の試行は新しいrunに保存し、正常対照の発話を取得できない試行や操作条件がそろわない試行は判断保留とする。選んだ入力エラー状態の所見と、WCAG 2.2 AAの対象範囲全体の結論は帳票でそれぞれ確認する。[タスク](../tasks/T026-process-error-speech.md) · [再実行と証拠](../../validation/development/T026/README.md)
