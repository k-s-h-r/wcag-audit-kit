# 0125 予約カレンダーで次の空きまでの操作と発話を比べる

## 背景

完成像では、予約できるサイトでも空きのない日を一日ずつ聞く負担がある場合に、改善を提案したい。T023とT027で扱ったのは予約人数と確認ボタン、T029で扱ったのは空き状況を色以外で見分けられるかだった。[VISION](../VISION.md#アクセシビリティ点検モード) · [T027](../tasks/T027-accessibility-review-workflow.md) · [T029](../tasks/T029-audit-availability-without-color.md)

## 決定

同じ日付と空き状況を持つ二つのローカルページを用意し、片方に「次の空き」ボタンを加える。共通の開始日と最初の空きを固定し、日付と空き状況が表示されて実Orcaがその情報を出力したところで計測を終える。実入力の回数と、日付・空き状況を組にした発話の回数を数える。試験担当にはURLと利用目的だけを渡して、同じ日へ自分でたどれるかを別に確認する。

所見は `wcag-audit-kit` の点検手順の書式でまとめる。通常の `page-audit` が初期画面から作る検査票を併記し、達成基準の判定に必要な追加確認を残す。[点検の手順](../../skills/wcag-audit-kit/references/accessibility-review.md)

## 代替案

ブラウザーが公開する名前やライブ領域から、表示と公開された意味を確認できる。実際にOrcaがどの案内をいつ出力したかを数えるため、入力後の観察窓をOrcaの原始ログと照合する。各入力後の観察時間をそろえたため、所要時間による改善効果は評価の対象外とする。

## 影響

点検手順、CLI、採点器は既存のものを使う。扱うのは一つの合成カレンダーでの空き確認まで。空きがない期間の終端、月境界、日付を選んだ後の予約や、他の支援技術・利用者への効果は追加検証になる。

## 検証方法

対照ページ、操作、到達条件を先にハッシュで固定する。両例を個別のブラウザーとOrcaセッションで順番に操作し、入力・表示・フォーカス・発話を照合する。URLだけで始めた担当の操作結果と、通常CLIの初期帳票も保管する。[再現と原本](../../validation/development/T041/README.md)
