# 0011 達成基準別の問題集と独立した採点処理を用意する

日付：2026-11-16 / 状態：Proposed

## 背景

従来の試験ページは機能・アダプター別に分かれ、[ADR 0010](0010-selectable-verification-modes.md)の対応表も検査手段の準備状況を示していた。基準ごとの既知の問題・正常例・期待結果を固定し、モードごとの検出と変更前後の回帰を共通の形式で比較する仕組みがなかった。

## 決定

benchmarks/cases/達成基準番号へsuite.jsonとpublicを置く。publicに必要なHTML・画像・音声・字幕等を同梱し、複数ページ・操作後の状態も1ケースに含める。suite.jsonは正解・根拠・モードの評価条件を持つ採点側の資料とし、検査担当へは正解を除いたジョブと公開ファイル・証拠だけを渡す。HTTPの公開範囲もpublicに限定する。

正解はページ・状態・論理的な対象・確認観点に結び付ける。欠落・誤った意味・機能不全を区別し、正常例・例外・同等な代替経路も含める。論理部品と細部の指摘位置は公開するtarget_aliasesで対応付け、判定は公開しない。初版は7基準・18ケース・20ページ・27観点とし、残る79基準は未整備と報告する。作成者が定めた対照例であり、全基準の網羅や専門家による独立した正解確認を表明しない。

収集には実際のaudit.py page-auditを使う。自動の採点接続は、現行パイプラインが出力するimage-alt、document-title、キー到達・送出の観察に限定する。属性や入力の成功から意味・機能・WCAG全体の適合を作らない。その他のAI・機械・実SRの観察は、同じ証拠付きの提出形式で追加する。実SRは実際の環境・対照発話が必要とし、AXツリーや環境全体の沈黙をページの結果に置き換えない。4.1.3の対照例専用の任意のOrca workerを用意する。

入力・正解・素材・実装・実行上限・ブラウザー等の環境・原典を固定する。実行中断後は完了済みのページを保持し、未完了ページを新しいattemptへ記録する。観察の追加・修正は履歴として保存し、過去の証拠や別の観点を消さない。採点結果も別のreportsへ保存する。

採点は検出・見逃し・誤検出に加え、未確認とモードで省く観点を区別する。未確認や未整備を成功へ数えない。変更前後は問題集・モード・対象・設定・環境・原典・採点器が一致する場合だけ比較する。既存の正答が誤りや未確認になった場合、新しい誤検出が増えた場合を回帰とする。「新しい回帰なし」と「全ての観点を確認できた」は別に報告する。

## 代替案

- 問題を含むページだけでは、全てを不適合とする検査を高精度と誤認する。
- 正解をページ・ファイル名・検査担当の入力へ含めると、実ページの観察による判定を試せない。
- 正解と実装の出力を同じ処理から生成すると、検出方法の誤りを発見しにくい。
- 全86基準へ空のファイルを置いて成功扱いすると、未整備の範囲が分からなくなる。
- 新しい方法で古いrunの証拠・判定を上書きすると、変更前後の比較と再現ができなくなる。

## 影響

通常のスキル配布とは分けた開発用の問題集・実行器・作業手順・HTML／JSON／Excelの採点を追加する。既存のWCAG検査定義・検出実装・スキル版・保存済み判定は変更しない。問題集の拡充、第三者による正解の確認、未公開の例による評価は今後も必要になる。方法の準備状況の表と、実際の問題集に対する実測を分けて管理する。

## 検証方法

全て問題なしとする結果、見逃し・誤検出、未確認の成功化、モード違反、別ジョブの証拠、画像・複数ページ・実発話の不足を拒否・検出する。分割取り込みの累積と過去記録の保持、再開、正解・素材の改変、比較条件の変更を検査する。実ブラウザーで対照例の挙動と公開範囲を確認し、実パイプラインの4モード収集・採点・帳票・比較を実行する。利用可能な環境では実Orcaの対照例も確認し、環境不足なら未確認として記録する。試験した範囲と未測定の方法を報告する。

実行結果・帳票の確認・未測定の方法は[検証記録](../../validation/criterion-benchmarks/README.md)に残す。
