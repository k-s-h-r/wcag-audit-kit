# 0102 修正前後で同じ対象の検査結果を照合する

日付 2026-11-21。状態はProposed。

## 背景

T013では同じフッターのリンクが、周囲のCSSによってページごとに異なるコントラストを示した。共通部品の修正を評価するには、前後の検査票からページごとの変化を追える必要がある。[VISION](../VISION.md#直したあとにもう一度使いたい) · [T013](../tasks/T013-site-selection.md#共通部品の同じ初期表示の測定を参照)

## 決定

`compare-reports` は別runの報告JSONを二つ読む。検査定義と適合レベルをそろえ、URL、状態、環境、達成基準、対象の識別文字列、期待結果が一致する行を比べる。ブラウザーの言語設定と版、遷移先も収集元の記録で確認する。言語を指定していないrunは既定の `ja-JP` として扱う。

帳票に記載された判定を、その帳票が参照する判定リビジョンと照合する。後から同じ検査票に判定が追加されても、以前の帳票が参照するリビジョンを使える。各側の対象の証拠を保存されたハッシュと照合し、その対象に同じ収集画面の証拠か同じ検査票への添付が1件以上あることも確かめる。

`page-audit` で画面を収集できたときは、起動したブラウザーの版を保存する。収集した状態、要素一覧、axe結果のURLが一致するときは、その実際のURLも保存する。記録が欠ける画面は比較で未確認とする。

同じ対象で不適合から通過に変わった行は解消、通過から不適合は新規、両方で不適合なら継続とする。未実施、判断保留、対象や条件の差、証拠不足には未確認の理由を添える。比較できる対象があっても、検査票に残る未確認の範囲は別の行に残す。

## 代替案と影響

不適合箇所の一覧だけを前後で引き算すると、修正後に未実施だった判定が解消と同じように見える。基準全体の結果だけでは、同じ基準で別の対象に起きた不適合を見分けにくい。対象単位の記録を照合して、条件が違うときは未確認の理由を出す。

比較は既存の帳票と証拠を読み、新しいJSONまたはHTMLに出す。元のrunは読取り専用で扱う。同じ共通部品でもページごとの観察を使う。認証の一致や設定にない状態の再現を確認できない場合は未確認を返す。

## 検証方法

通常のCLIで二つのrunを作り、同じリンクを置いたページのコントラストをChromiumで測る。解消・新規・継続に加え、判定を記録していないページ、HTTP 404、範囲から外れたページを用意する。比較HTMLのリンク、証拠のハッシュ、原本の不変を確認する。[試験手順と結果](../../validation/development/T025/README.md)
