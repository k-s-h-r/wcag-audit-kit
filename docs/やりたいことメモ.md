# やりたいこと

- webページのWCAGチェックを行える
- 機械でできるところは機械で、機械でできない部分はAIで行いたい
- 人間が行うようなWCAGチェックを人間なしで行えるようにすることが最終目標

公開されている1ページは、URLを渡せば検査を始められるようにしたい。サイト全体なら調べたい範囲を伝え、ログインやテストデータが必要なら先に用意する。検査対象を見つけ、実際に操作し、判定と証拠を報告にまとめるところまで進める。段階的な到達目標はWCAG 2.2 AA。


## 機械でやりたい部分

- AXEのような自動検査
- HTMLが正しく利用されているか
- キーボードの閉じ込めがないか
- URLからリンク、ボタン、入力欄などを見つけ、クリックやTab・Enter・Spaceを実際に試す。操作で新たに表示された内容も検査する
- キーが届いたことと、機能が動いたことを両方確かめる。例えば、数量が増えたか、メニューを閉じた後どこにフォーカスが戻ったかを記録する
- PC幅とスマホ相当の幅で確認し、必要に応じて文字の拡大、色のコントラスト、フォーカスの見え方を測る
- 見出しの階層、フォームのラベルと入力欄、表の見出しとデータの対応を、ブラウザーが認識した情報から確かめる。ARIA属性が少ないページでも、標準の部品や実際の操作をもとに検査できるようにする

## AIでやりたい部分

- 画像のaltが正しく入っているか
- 画像が装飾か装飾じゃないか判断
- 音声や動画の代替があるか
- 画像のaltや字幕ファイルの有無は機械で集める。内容を調べるときは、画像が伝える情報と代替文、音声や映像の重要な情報と字幕・文字起こし・音声解説を照らし合わせる
- ページ本文とタイトルが合っているか、リンク先やボタンの目的が文脈から分かるか、エラーの説明で何を直せばよいか伝わるかを確かめる
- 画面を見て、見た目はボタンなのに役割や操作方法が伝わらない部品を探す。AIが新しい操作候補や表示状態を見つけたら、その状態にも機械検査をかける

## 実際のスクリーンリーダーで確かめたいこと

使える環境では、読み上げ順、部品の名前や状態、操作後の通知を、実際の操作と発話で確かめる。例えば、保存ボタンを押したときに、画面に出た完了通知が読み上げられるかを見る。

## サイト全体を頼まれたとき

基準URLやサイトマップから候補を集め、認証後のページや操作後に現れる画面も調べる。どのページを選んだかと、その理由を残す。フォームの入力からエラーの修正、送信後の確認までのように、複数の画面にまたがる手続きは一通り試す。

## 受け取りたい結果

まずHTMLで、修正が必要な箇所と、検証がどこまで済んだかが分かる。各指摘には、達成基準、URL、対象の部品、画面状態、再現手順、期待した結果と実際の結果を載せる。スクリーンショットや操作ログ、発話の記録など、判断に使った証拠を開けるようにする。

適合・不適合・対象外に加えて、未探索や判断保留も見えるようにする。例えば、権限が足りず確認できなかった画面には、必要な権限と追加で試す操作を残す。ExcelやJSONでも結果を受け取れ、修正後に同じ条件で再検査して前回と比べられる。

## できるようになったかの確かめ方

問題例と正常例を用意したベンチマークでは、URLと共通の設定だけを渡して測る。既知の問題のうち正しく指摘できた件数を主な成績にし、誤検出、操作や状態の未発見、到達後の判断保留も別々に数える。標準HTMLを使った正常例と、見た目が似ていてもキー操作や意味づけに問題のある例の両方を確かめたい。

問題集で安定したら、実際のサイトやアプリでも同じ進め方を試す。検査していない状態や、必要な手段が使えなかった観点をどこまで報告できたかも確認する。実装の順序と現在地は[開発計画](ROADMAP.md)に記す。
