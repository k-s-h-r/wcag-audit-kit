# やりたいこと

URLからページや一連の手続きを自分で見つけて試せるスキルにしたい。軸は、決めた範囲がWCAGに適合しているかを根拠と一緒に答えること。

## 目的に合わせて選びたい二つのモード

### WCAG検証モード

- **各ページのWCAG未対応箇所の一覧**。どの画面で何をすると問題が起き、どの達成基準を満たしていないかが分かる。画面や操作の記録を見れば、直す人も同じ問題を再現できる。
- **WCAG検査票**。決めた範囲の適合・不適合の結論から、達成基準ごとの判定と根拠までたどれる。判定に必要な確認が残っていれば、どこを確かめればいいかも分かる。

### アクセシビリティ点検モード

日々の開発や運営で、誰がどんな操作でつまずくかと、負担を減らすための改善案を受け取りたい。たとえば、読み上げで予約できるサイトでも、空きのない日を一日ずつ聞いて回るのは手間がかかる。「次の空き」に直接移れると助かる、といった提案までほしい。

## 人が使うように、最初から最後まで試したい

たとえば予約サイトなら、メニューから予約の入口を見つけ、空いている日を選び、入力の間違いを直して、確認画面に着くところまで。キーボードだけで同じ手続きをたどれるか、エラーが出たときにスクリーンリーダーで何が聞こえるかまで確かめたい。

## 機械とAIに任せたいこと

- axeを使った自動検査や、HTMLの使い方の点検は機械に任せたい。キーボードでボタンやフォームを実際に操作して、途中で抜け出せなくなる場所がないかも確かめてほしい。
- AIには、画面を見て次に何を試すか考えてほしい。たとえば空きを色分けしたカレンダーなら、文字や記号でも空きが分かるかを確かめて、WCAGの「1.4.1 色の使用」の判定に使う。
- 画像が飾りなのか、説明に必要なのかを、周りの文章と合わせて判断してほしい。代替文から画像の内容が伝わるか、字幕や書き起こし、音声解説から動画や音声の大事なところが分かるかも見てほしい。
- 初めて来た人のつもりで、見出しから欲しい情報を探せるか、リンクやボタンの名前から押した先を想像できるか、エラーの案内を読んで入力を直せるかを確かめたい。
- 検査票を書いている途中で根拠が足りないと気づいたら、その画面に戻って、操作を変えたり、読み上げを聞いたりしてから答えを出してほしい。

## 直したあとに、もう一度使いたい

共通のメニューに問題があったら、どのページに影響しているか一覧で分かるといい。メニューを直したらもう一度WCAG検証を頼み、どのページで解消したか、今回の変更で新しい問題が出ていないかを前の検査票と見比べたい。

## 何ができたら前進か

WCAGの問題集では、URLから自分でどこを操作するか判断し、その先にある問題まで見つけられるかを確かめたい。同じ見た目の正常例では、基準を満たすと判断した根拠も示せるようにしたい。
