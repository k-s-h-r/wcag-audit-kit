# アクセシビリティ点検

点検では、利用者が何をしようとしてどこでつまずくかを調べ、負担を減らす変更と、その効果を確かめる方法を返す。達成基準の判定がある場合は、元の検査票と証拠を参照できるようにする。

## 保存済みの観察を使う

1. 指定されたrun、帳票、操作記録から、対象の版、URL、手続き、状態、環境を確認する。帳票の `scope_conformance` や検査票で保存済みの判定を読み、操作ログ、画面、DOM、アクセシビリティツリー、実際の発話など、所見の根拠までたどる。同じ操作でも版や環境が異なる場合はそれぞれ明記する。
2. 読める記録を使って、利用目的、行った操作、観察結果を書く。証拠が欠ける箇所は、何が分からず、どの観察を追加すれば確かめられるかを記す。保存済みの記録は読み取り専用で扱い、追加の観察は依頼を受けたときに行う。

## 対象URLから観察する

1. 指定されたURLと、達成したい操作を確認する。手続きが指定されていなければ、画面から主要な操作を一つ選び、選んだ範囲を示す。環境と観察に使う手段は依頼に従う。新しい単独の観察で検査手段の指定がなければ、まず機械検査で収集できる証拠を使う。[検証モード](verification-modes.md)
2. 新しいrunで[1ページの収集と操作探索](page-audit.md)を使う。初期表示と操作前後を調べ、実際の入力、フォーカス、表示や値の変化、到達した状態を記録する。別ページへ続く手続きは、画面から分かる経路を依頼の範囲で試す。ページ別のrunや追加の操作ログを使った場合は、どの操作と画面の証拠かが分かるように点検結果から参照する。[対象固有の操作手順](methods.md#対象固有の操作手順を実行して確かめる)
3. 送信・予約確定・削除などを伴う場合は、許可されたテスト環境と操作の範囲に従い、止めた場所を記録する。上限、認証、実スクリーンリーダーなどの不足で確かめられない操作も残す。アクセシビリティツリーで見た名前や状態は、取得した根拠を添えて記し、実際の発話を確認した場合は、操作と発話を対応付ける。

## 開発・運営の担当者に結果を渡す

回答は点検結果としてまとめる。ファイルを頼まれた場合は新しいMarkdownに保存する。所見ごとに、読み手が同じ箇所を再現して改善を試せる情報を記す。

操作に成功した場合も、何度も移動する必要があるなど、実際に観察した負担を記す。達成基準の既存判定がある場合は、その判定と観察した負担を併記する。

| 項目 | 記載する内容 |
| --- | --- |
| 操作と観察 | 利用目的、URL・画面・対象、状態・環境、再現手順、観察結果、実在する証拠への参照 |
| 利用への影響 | どの入力方法や利用状況で、どの操作が止まるか、余計な手順が必要か。推定した影響には根拠を添える |
| 改善案 | どの部品・案内・操作をどう変えると、観察した負担を減らせそうか |
| 効果を確かめる方法 | 同じ出発点、入力方法、環境で何を見比べるか。到達可否、余分な操作の回数、案内や発話など、操作に合う指標と期待する結果 |
| 比較結果と未確認 | 前後を比較できる証拠があれば実測値と両方の証拠。なければ効果を未確認とし、未探索の経路や、支援技術・利用者による確認の要否も示す |
| 関連するWCAG判定 | 確認した版・レベル・範囲、該当の基準、元の判定と検査票IDや帳票。参照できる判定がなければ未確認と示し、機械検査の候補にはその旨を添える |

例えば、予約の増員ボタンにTabで移動し、EnterとSpaceのどちらを押しても1名のままだったとする。同じ操作箇所をクリックして2名になったなら、その経路でキーボード利用者が増員できなかったと記録する。標準のボタンに替える案なら、同じ開始画面からキーで2名に変更でき、確認画面に正しい人数が出るかを測る。変更前後の版、比較条件、証拠を記す。

改善案の適用は別の依頼で扱う。確認対象に修正後の版が含まれる場合は、同じ条件で再測定し、新しいrunに結果を保存する。WCAG検証も依頼された場合は通常の手順で検証し、[保存済みの検査結果の読み方](checksheet.md)に従って参照先を示す。元の台帳・判定・原始証拠は読み取り専用で扱う。
