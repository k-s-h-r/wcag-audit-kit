# 1ページを実際に検証する

入力はURL、必要なら既存run・タスク・認証・状態の到達手順。出力はページの各基準の判定、画像から調べた操作・状態、証拠、必要な人への確認。利用者に基準番号を選ばせない。

利用者がこのスキルを明示して開始する。全体監査では、明示された監査のページ担当手順としてこのファイルを読む。通常の開発や相談から独立した監査を自動で始めない。

## 実行ルートと開始

このSKILL.mdがあるディレクトリーを実行ルートとする。同梱の`scripts/`・`references/`・`assets/`・`vendor/`を使い、コマンドはこのディレクトリーから実行する。

### 新規検査の設定を確認する

利用者から直接、1ページの新規検査を依頼されたら、依頼文と指定された設定ファイルを読み、足りない項目を実行前にまとめて聞く。明示された値は聞き直さない。回答が来るまでページへのアクセスとrunの作成を待つ。

- 適合レベルは A、AA、AAA（推奨はAA）。
- 検査モードは機械のみ、AI併用、スクリーンリーダー併用、AIとスクリーンリーダーの両方（推奨は機械のみ）。
- 標準の証拠画像は撮らない、初期表示だけ、状態ごと、操作途中も（推奨は初期表示だけ）。初期表示だけを選ぶと、操作する前のページ全体を既定のPC幅とスマホ相当の幅で1枚ずつ保存する。操作前後の画像は、その時点で表示されている範囲を撮る。

足りない項目ごとに上の選択肢を示し、一度の回答で指定できるようにする。「おまかせならAA・機械のみ・初期表示だけ」と案内し、利用者が判断を任せた項目にはこの設定を使う。表示幅や画像の枚数上限は指定があれば反映する。ログインや追加の操作が検査に必要な場合は、その条件も確認する。

既存runの再開・報告、親のサイト監査から設定を受け継いだページ担当では、保存済み又は上位で確定した設定を使う。新規検査の確認を繰り返さない。機械検査で画像を保存する場合も、AIによる画像・内容の判断は行わない。

新規の独立した1ページは、確認した値をCLIへ明示し、まず初期画面だけを機械検査する。AA・機械のみ・初期画像だけなら、次のように指定する。

```sh
python3 scripts/audit.py page-audit --url <URL> --out <新しいrun> --level AA --mode machine --screenshots initial --initial-only
```

初期画面の収集が終わったら、機械検査で検出した問題とHTMLへのリンクを途中経過としてすぐ共有する。そのまま同じrunで簡易探索を実行し、最終結果を返す。操作探索を始めるための追加確認は不要。利用者が初期画面の検査だけを明示した場合は、初期結果で終える。

```sh
python3 scripts/audit.py page-audit --url <URL> --out <同じrun> --resume --quick-explore
```

操作探索後は同じHTML・JSON・Excelに結果が入る。予定の範囲に収まらなかった操作を未確認として伝える。利用者が最初から詳細な自動探索を明示した場合は、初期結果を共有してから上記の `--quick-explore` を `--explore` に替える。指定の操作経路は、設定済みの手順やprobeで確認する。初期画面の機械検査以外にAIの判断・実SRの確認などを依頼されている場合は、初期結果の共有後に、依頼された手段と範囲で進める。保存済みの記録から報告だけを更新する場合は `page-report` を使う。

認証や表示環境には`--config <設定>`を渡す。枚数上限が指定されていれば`--max-images`にも渡す。事前設定のstatesを収集する検査は既存のpageコマンドを使い、自動探索に追加の独自シナリオが必要ならprobeで検査する。単独入口は指定URLだけを収集し、リンクを巡回しない。設定未指定時の初期環境はdesktopとnarrow。実拡大等の追加環境は、基準に応じて調べ、設定又は追加検証で用意する。

既存runの担当なら収集を繰り返さず、`page-next --run <run> --page-exact <URL>`又は`pending --run <run> --page-exact <URL> --task <ID>`から読む。機械検査の収集成功は検証完了ではない。

公開URLを開くだけで始められる検査は、設定が揃ったらそのまま進める。認証・アプリ起動・特定状態への到達が必要なら、[対象固有の操作手順](references/methods.md#対象固有の操作手順を実行して確かめる)を必要な範囲で用意する。実行確認済みの経路と未確認の経路を分け、準備の失敗をWCAG不適合へ読み替えない。

## 検証モードに従う

[モードの仕様](references/verification-modes.md)のmachine / ai / screen-reader / fullを使う。対話からの新規検査は確認したモードを使う。CLIを直接実行する場合の既定はmachine。利用者が選んだモードを固定し、AIや実SRを使うために黙ってfullへ切り替えない。変更した検査は新しいrunにする。既存runにモードがなければ従来の観察設定に従う。

page-nextのverificationとverification_checkpointsを読む。AIが無効なら画像・文章の意味や見た目をAIで判断せず、機械の有無・数値・実入力・明示した期待値の比較に絞る。実SRが無効なら起動しない。×の観点は省略理由と残る確認を記録し、対象外や適合に変更しない。△は検査できた部分だけを記録する。

AIが有効なら利用できる保存画像・本文・操作結果を比較する。画像の比較に必要な証拠がなければ未確認に残す。実SRが有効なら対応環境を調べ、ページ専用のシナリオを準備し、既存アダプターで実操作・発話を取得する。環境不足や未実行を実施済みにしない。CLI単体ではAIの判断・実SRの起動は行わない。

AIが有効なモードで画像の代替説明を判断するときは、画像から読んだ情報と、代替説明や操作後の本文から得た情報をそれぞれ記録し、ページの目的に必要な情報が対応するかを示す。画面全体から対象を読み取れない場合は、保存画像の対象部分を原寸で切り出し、元画像と切り出し範囲を証拠に添える。対応を確認できなかった部分は未確認に残す。

## 機械検査から自律的に進める

[1ページの実行手順](references/page-audit.md)を使う。簡易探索では、PC幅とスマホ相当幅の両方で、主要な操作、新しく現れた部品、開閉などの状態変化を優先する。自動で続けるのは既定の1回まで。上限や候補の絞り込みにより残った操作は `page-next` と帳票に記録する。自動検出した対象以外は、AIが有効なモードでは画像から追加確認する。

追加検査を依頼された範囲では、まず機械ルール・実操作・測定・既存アダプターで確認し、意味・目的等で必要な部分だけ内容判断する。実行できる検査を手順だけ書いて人へ渡さない。方法が足りなければ代替を調べ、小さい経路で実行を確かめて続ける。人の権限や専門判断が必要になった場合だけ具体的な引き継ぎを作る。

追加検査では実行した担当票をrecordし、page-nextから次の票へ進む。探索の解消にはその版に対応する追加証拠を保存する。既存の画像・判定を変更しない。未確認を適合へ変えてループを終了しない。機械ルールの通過やTabによる到達だけで基準全体を確定しない。

## 画面から操作と状態を調べる

[画面の調査手順](references/visual-discovery.md)を読む。AIが有効なモードでは、保存した画像を画像表示ツールで実際に見る。見た目、ラベル、位置から、リンク、ボタンに見える領域、メニュー、入力、開閉、ドラッグ等を列挙する。divかbuttonかは、その後にDOM・ツリーと対応付けて調べる。コード上のイベント検索だけで候補を確定しない。

各候補について、到達・開始・内部操作・終了・閉じた後のフォーカスを実際の入力で確認する。初期表示だけでなく、開いた後、入れ子、エラー、条件付き表示も調べる。モーダル内のTab循環を、それだけでキーボードトラップとしない。

操作する経路とテスト環境を確認する。送信・削除等を無差別に実行しない。未探索の対象と、追加で必要な画像・環境・操作を残す。新しい状態が設定に必要なら元のrunを保持して新しい設定・runで収集する。

画像を観察するモードでは、ページごとの[操作調査票](assets/interaction-review.example.json)を実際の画像・操作へ具体化し、`review-interactions --run <run> --file <票>`で保存する。調査票の版はplanのinteraction_reviewsから読む。初回のbase_reviewはnull。

## 基準ごとに検査する

1. `case --run <run> --id <case_id>`から対象・本文・手順・版を取得する。該当基準の原文、例外、公開テストを必要な分だけ読む。
2. 全対象へ操作・期待結果・観察方法を具体化する。選択したモードで許可された画面・意味・操作を実際に比較し、使わない方法は未確認に残す。axeやDOMの属性だけを基準全体の通過にしない。
3. [方法一覧](references/methods.md)から必要な道具を使う。実SRがrequiredなら実際の支援技術で確認する。ツリーやVirtual Screen Readerを実SRと呼ばない。使用できなければ具体的な引き継ぎを記す。
4. [記録規約](references/recording.md)に従いrecordする。共同作業はbase_assessmentで版を照合する。未実施の票を残したまま全基準確認済みとしない。
5. ページ間比較・手続き全体が必要なら、必要なURL・状態・操作を残して全体進行へ返す。単独ページだからという理由で対象外にしない。

## 観察の予算と終了

[観察設定](references/inspection-profiles.md)を使う。追加の検査でも、合意した撮影範囲を守る。画像が必要な観点で撮影範囲に含まれない画面や操作は未確認として残す。画素を使うコントラスト測定を明示された場合は、その測定に必要な画像を取得する。SRの省略と適用対象の不在も区別する。

追加検査に進んだ場合は担当票に判定又は具体的な引き継ぎを記録し、未探索の操作・状態・省略した観察を渡す。追記した判定を反映するときは、`page-report --run <run> --page-exact <URL>`でページ別の帳票を更新する。

利用者にはまず閲覧用HTMLのパスと検証状態を伝える。処理用JSONは検査の引き継ぎに使う。`audit_complete`が`false`なら「帳票を作成しました。検証は未完了です」と伝え、検査票や探索などの残作業を報告JSONから示す。機械ルールが検出した問題は対象箇所とルール名を添えて伝え、達成基準全体の判定は記録済みの判定から示す。サイト全体の適合を宣言しない。
