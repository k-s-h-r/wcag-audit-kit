# 1ページを実際に検証する

入力はURL、必要なら既存run・タスク・認証・状態の到達手順。出力はページの各基準の判定、画像から調べた操作・状態、証拠、必要な人への確認。利用者に基準番号を選ばせない。

利用者がこのスキルを明示して開始する。全体監査では、明示された監査のページ担当手順としてこのファイルを読む。通常の開発や相談から独立した監査を自動で始めない。

## 実行ルートと開始

このSKILL.mdがあるディレクトリーを実行ルートとする。同梱の`scripts/`・`references/`・`assets/`・`vendor/`を使い、コマンドはこのディレクトリーから実行する。

独立した1ページなら、実行ルートから次を実行する。

```sh
python3 scripts/audit.py page-audit --url <URL> --out <新しいrun> --mode machine
```

`page-audit`は初回も`--resume`も、成功時にページ別のHTML・JSON・Excelを出力する。機械検査の結果を渡すときは、このコマンドが返したパスを案内する。判定を追記した後や、保存済みの結果から帳票を作り直す依頼では`page-report`を使う。

認証や表示環境には`--config <設定>`を渡す。事前設定のstatesを収集する検査は既存のpageコマンドを使い、自動探索に追加の独自シナリオが必要ならprobeで検査する。単独入口は指定URLだけを収集し、リンクを巡回しない。設定未指定時の初期環境はdesktopとnarrow。実拡大等の追加環境は、基準に応じて調べ、設定又は追加検証で用意する。

既存runの担当なら収集を繰り返さず、`page-next --run <run> --page-exact <URL>`又は`pending --run <run> --page-exact <URL> --task <ID>`から読む。機械検査の収集成功は検証完了ではない。

公開URLを開くだけで始められる検査はそのまま進める。認証・アプリ起動・特定状態への到達が必要なら、[対象固有の操作手順](references/methods.md#対象固有の操作手順を実行して確かめる)を必要な範囲で用意する。実行確認済みの経路と未確認の経路を分け、準備の失敗をWCAG不適合へ読み替えない。

## 検証モードに従う

[モードの仕様](references/verification-modes.md)のmachine / ai / screen-reader / fullを使う。未指定で新しい単独検証を始める場合はmachine。利用者が選んだモードを固定し、AIや実SRを使うために黙ってfullへ切り替えない。変更した検査は新しいrunにする。既存runにモードがなければ従来の観察設定に従う。

page-nextのverificationとverification_checkpointsを読む。AIが無効なら画像・文章の意味や見た目をAIで判断せず、機械の有無・数値・実入力・明示した期待値の比較に絞る。実SRが無効なら起動しない。×の観点は省略理由と残る確認を記録し、対象外や適合に変更しない。△は検査できた部分だけを記録する。

AIが有効なら保存画像・本文・操作結果を実際に比較する。実SRが有効なら対応環境を調べ、ページ専用のシナリオを準備し、既存アダプターで実操作・発話を取得する。環境不足や未実行を実施済みにしない。CLI単体ではAIの判断・実SRの起動は行わない。

AIが有効なモードで画像の代替説明を判断するときは、画像から読んだ情報と、代替説明や操作後の本文から得た情報をそれぞれ記録し、ページの目的に必要な情報が対応するかを示す。画面全体から対象を読み取れない場合は、保存画像の対象部分を原寸で切り出し、元画像と切り出し範囲を証拠に添える。対応を確認できなかった部分は未確認に残す。

## 機械検査から自律的に進める

[1ページの実行手順](references/page-audit.md)を使う。page-auditはAIサービスへ接続せず、操作候補・状態のキューを探索し、実状態ごとのaxeと実入力の結果を記録する。page-nextで残作業を読み、キューが残れば適切な上限で--resumeする。自動検出した対象以外は、AIが有効なモードでは画像から追加確認する。

まず機械ルール・実操作・測定・既存アダプターで確認し、意味・目的等で必要な部分だけ内容判断する。実行できる検査を手順だけ書いて人へ渡さない。方法が足りなければ代替を調べ、小さい経路で実行を確かめて続ける。人の権限や専門判断が必要になった場合だけ具体的な引き継ぎを作る。

各担当票をrecordし、page-nextから次の票へ進む。探索の解消にはその版に対応する追加証拠を保存する。既存の画像・判定を変更しない。未確認を適合へ変えてループを終了しない。機械ルールの通過やTabによる到達だけで基準全体を確定しない。

## 画面から操作と状態を調べる

[画面の調査手順](references/visual-discovery.md)を読む。AIが有効なモードでは、保存した画像を画像表示ツールで実際に見る。見た目、ラベル、位置から、リンク、ボタンに見える領域、メニュー、入力、開閉、ドラッグ等を列挙する。divかbuttonかは、その後にDOM・ツリーと対応付けて調べる。コード上のイベント検索だけで候補を確定しない。

各候補について、到達・開始・内部操作・終了・閉じた後のフォーカスを実際の入力で確認する。初期表示だけでなく、開いた後、入れ子、エラー、条件付き表示も調べる。モーダル内のTab循環を、それだけでキーボードトラップとしない。

操作する経路とテスト環境を確認する。送信・削除等を無差別に実行しない。未探索の対象と、追加で必要な画像・環境・操作を残す。新しい状態が設定に必要なら元のrunを保持して新しい設定・runで収集する。

画像を観察するモードでは、ページごとの[操作調査票](assets/interaction-review.example.json)を実際の画像・操作へ具体化し、`review-interactions --run <run> --file <票>`で保存する。調査票の版はplanのinteraction_reviewsから読む。初回のbase_reviewはnull。

## 基準ごとに検査する

1. `case --run <run> --id <case_id>`から対象・本文・手順・版を取得する。該当基準の原文、例外、公開テストを必要な分だけ読む。
2. 全対象へ操作・期待結果・観察方法を具体化する。選択したモードで許可された画面・意味・操作を実際に比較し、使わない方法は未確認に残す。axeやDOMの属性だけを基準全体の通過にしない。
3. [方法一覧](references/methods.md)から必要な道具を使う。実SRがrequiredなら実際の支援技術で確認する。ツリーやVirtual Screen Readerを実SRと呼ばない。使用できなければ具体的な引き継ぎを記す。
4. [記録規約](references/recording.md)に従いrecordする。共同作業はbase_assessmentで版を照合する。未実施の票を残したまま全基準確認済みとしない。
5. ページ間比較・手続き全体が必要なら、必要なURL・状態・操作を残して全体進行へ返す。単独ページだからという理由で対象外にしない。

## 観察の予算と終了

[観察設定](references/inspection-profiles.md)を使う。画像なしでは画面の操作対象を調査済みにせず、見ていない画像を読んだと記録しない。SRの省略と適用対象の不在も区別する。

今回の担当票に判定又は具体的な引き継ぎを記録し、未探索の操作・状態・省略した観察を渡す。追記した判定を反映するときは、`page-report --run <run> --page-exact <URL>`でページ別の帳票を更新する。

利用者には帳票のパスと報告JSONが示す検証状態を伝える。`audit_complete`が`false`なら「帳票を作成しました。検証は未完了です」と伝え、検査票や探索などの残作業を報告JSONから示す。機械ルールが検出した問題は対象箇所とルール名を添えて伝え、達成基準全体の判定は記録済みの判定から示す。サイト全体の適合を宣言しない。
