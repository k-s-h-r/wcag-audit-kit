# 1ページを機械検査から始める

```sh
python3 scripts/audit.py page-audit --url https://example.com/contact --out /project/run-page --level AA --mode machine --screenshots initial
python3 scripts/audit.py page-next --run /project/run-page --page-exact https://example.com/contact
```

page-auditは、対象URLだけで操作候補を調べ、実クリック・hover・Tab・Enter・Space・部品ごとの矢印キー等で到達した状態を収集する。状態ごとにDOM、アクセシビリティツリー、実入力、axeの結果を保存する。画像は指定した撮影範囲に従う。LLMやAIサービスのAPIキーは必要ない。検証対象はテスト用環境を使い、認証が必要なら既存の設定のauth_stateを指定する。事前設定のstatesを含む設定は既存のpageで収集する。page-auditでは自動探索を使い、必要な独自シナリオをprobeで追加検査する。

操作候補はネイティブ部品・ARIA・登録されたイベント・カーソル等から抽出する。開いた後に現れた候補もキューへ追加する。外観だけで操作できそうな領域の追加確認には、保存画像と位置・候補一覧を使う。候補抽出だけで全操作を発見したことにはしない。

直接 `wcag-page` に新規検査を頼む場合、適合レベル、検査モード、標準の証拠画像のうち未指定の設定を開始前に聞く。CLIを直接使う場合は各オプションで指定する。上の例では機械検査を行い、PC幅とスマホ相当の幅で、操作する前のページ全体を1枚ずつ保存する。ほかの撮影範囲と枚数上限は[観察設定](inspection-profiles.md)を参照する。

## 初期画面の結果を先に返す

```sh
python3 scripts/audit.py page-audit --url https://example.com/contact --out /project/run-page --mode machine --screenshots initial --initial-only
python3 scripts/audit.py page-audit --url https://example.com/contact --out /project/run-page --resume --quick-explore
```

直接の `wcag-page` は1行目で初期画面の結果を先に共有し、続けて2行目を自動で実行する。各環境のaxeと設定に応じた初期画像を保ち、操作後に得た結果を同じレポートに反映する。簡易探索では根拠のある操作や新しく現れた部品を優先し、各環境で通常の保留経路を最大12件に絞る。既定の上限は累計24ステップ、16状態、経路の深さ3。未実施の候補は省略数と理由を記録する。HTMLとJSONでは操作探索が未実施の間、その状態を表示する。初期画面の収集を中断した場合は `--resume --initial-only` で続きから収集できる。

補助CLIから通常の自動探索を使う場合、新規runは従来の呼び出しを使え、初期結果だけを収集したrunには `--resume --explore` を使える。

## 指定URL一覧を順に検査する

[設定](config.md)の `scope.mode` を `configured` にし、`scope.pages` 又は `scope.pages_file` に確定した一覧を指定する。検証モードは `machine`。自動探索用に既定の等倍環境を用意し、事前定義の `states` は空にする。URLは一覧の順に処理する。リンク巡回は行わない。

```sh
python3 scripts/audit.py page-batch --config /project/wcag.yml --out /project/run-pages --max-pages-this-run 10
python3 scripts/audit.py page-batch --config /project/wcag.yml --out /project/run-pages --resume --max-pages-this-run 10
```

`--max-pages-this-run` は1回に処理する件数で、省略すると残りをすべて処理する。停止後や上限到達後の再開には同じ設定・一覧・認証状態・検査の版を使う。`page-batch.json` からURLごとのHTML・JSON・Excel、未着手・中断・失敗理由を確認できる。404など収集できなかったURLは失敗として残し、続くURLへ進む。

`completed` はページ別帳票ができたことを表す。未探索の経路数、達成基準の判定件数、検証の完了状況は別の項目に記録する。帳票があるページの残りを検査する場合は、そのページのrunを使って `page-audit --resume` や `page-next` を実行する。バッチの台帳は帳票を作った時点の記録として残る。

### 共通部品のコントラスト測定をまとめる

指定URLの機械検査を実行した後、各ページで同じ部品に対して記録された色コントラストをまとめて読める。対象はaxeの `color-contrast` の `target` にある単一の文字列をそのまま指定する。環境は保存済み設定のIDを使う。

```sh
python3 scripts/audit.py shared-contrast --batch /project/run-pages --target '#shared-help' --environment desktop
```

JSONの `groups` に、同じ条件・内容の測定と、その測定を持つ各ページの証拠が出る。値が異なる測定は別グループになる。未着手・収集失敗・判定不能などは `unavailable` に理由を残す。各ページで取得した初期表示のaxe測定を読む機能で、ページごとの判定は検査票で確認する。

1ページを起点に参照するには、バッチ台帳にあるURLと、比較元とは別の新しい保存先を指定する。参照HTMLから、このページと同じ測定、異なる測定、未確認理由、元の証拠を追える。

```sh
python3 scripts/audit.py shared-contrast --batch /project/run-pages --target '#shared-help' --environment desktop \
  --page-exact 'https://example.test/products' --out /project/products-contrast.html
```

## 見た目の構造と認識された役割を確認する

1.3.1の確認で、見た目の構造とアクセシビリティツリーを比較するときは、設定の `visual_structure_scope` に主文書の領域を一つ指定する。例えば `"visual_structure_scope": "#article"` を設定して `page-audit` を実行する。既存のrunに追加する場合は、新しいrunとして検査する。

各環境の表示範囲で、次の候補をChromiumのアクセシビリティツリーと照合する。`machine` で画像を保存せず実行できる。

- **見出し**は、領域直下の `p` やテキスト主体の `div` のうち、直後の本文より大きく太字のもの。ブラウザーに見出しとして認識されているか確認する。
- **リスト**は、配置と書体がそろった3項目以上の箇条書きや連番。中黒、丸、ハイフン、`1.`、`1)` などの行頭を使う。`br` で区切った行は別項目として並んで見えるか、ブラウザー上で一つの項目にまとまっているかを確認する。
- **表**は、領域自身または直下にある、太字の先頭行と整列した後続行を持つ3〜8行・2〜6列の文字のまとまり。表、行、セル、列見出しの役割と所属を照合する。役割が不足している箇所のセレクターも出す。

後続の各行がブラウザーに独立した `article` として認識され、角の丸い枠と行間のすき間があるときは、カードのまとまりとして表候補から外す。表やグリッドの役割が指定されたまとまりは照合する。配置から目的を絞れない場合は確認候補に残す。

操作後に見える候補も調べる場合は、同じ設定に `"visual_structure_states": "explored"` を追加する。探索の件数・深さの上限内で新しく保存する画面を観察する。例えば、アコーディオンを開いた操作や、段落がCSSで見出し風になった操作と候補を対応付けられる。保存されない状態や表示範囲外の項目は、必要に応じて別の操作で確かめる。

HTML・Excelの「見た目の構造の確認候補」に、表示状態・操作、対象要素、ブラウザーが認識した役割、観察の証拠が出る。JSONでは各行・セルの照合結果も読める。太字の導入文や表に似た配置が候補になるため、伝えるべき関係を確認してから検査票を判定する。表の結合セル・複数段の見出しや、表示範囲外は追加で確認する。

## モードを選んで進める

[検証モード](verification-modes.md)のmachine / ai / screen-reader / fullを`--mode`で選ぶ。設定なしの新しいpage-auditはmachine。モードで有効な検査手段と、実際に実行した結果は区別する。page-nextは利用する観点・省く観点・理由を返す。AIによる比較はスキルの実行環境、実SRは専用アダプターで実施し、このCLIだけで両方を実行済みにはしない。モード変更は別のrunとし、resumeは保存したモードを継続する。

## 収集と再開

各経路を独立したブラウザーコンテキストで再生し、互いの入力・ストレージの影響を抑える。画面の表示内容・状態属性・値・色やアウトラインの変化で状態を区別する。同じ状態へ達した経路も、入力方式の違いと実行結果を残す。モーダルのEscapeも実際に試す。

探索で開いた主文書のモーダルダイアログをEscapeで閉じた場合は、開く操作の対象と閉じた直後のフォーカスを記録する。経路を再生し、その次のTabの移動先も探索上限内で観測する。Tabでフォーカスが動かない場合は、その結果を記録して判定を保留する。HTMLの「ダイアログを閉じた後のフォーカス」と、JSON・Excelの機械検査から実入力の証拠を追える。Escape以外の閉じ方や、開く操作とは別の位置にフォーカスを移す理由は追加で確認する。

`role="tablist"` 内の横並びタブでは、Tabで候補に到達して左右キーを試す。向きの指定を省略したタブリストも含む。フォーカスだけが別のタブに移った状態でも、続けてEnter・Spaceを試す。開いたパネルもその状態の機械検査に含まれ、フォーカス先や選択・表示の記録は操作経路の証拠から追える。期待する動作まで照合する場合は、下記のキーボード操作を指定する。

デフォルトは最大64状態、512経路、深さ8。上限や未到達は未確認として出力し、検証完了にしない。上限を広げて同じrunから続けられる。max-stepsとmax-statesは今回の追加件数ではなく累計上限。

```sh
python3 scripts/audit.py page-audit --url https://example.com/contact --out /project/run-page --resume --max-states 128 --max-steps 1000 --max-depth 12
```

探索はexploration.jsonへ保存する。再開時に過去の証拠のハッシュと探索実装の版を確認し、完了した経路と判定を保持する。探索中の状態は新しい証拠ディレクトリーへ保存し、既存の画像・判定を上書きしない。同じrunの探索を同時に2つ動かすことはできない。探索の実装が更新された場合は新しいrunを作る。画像の設定と上限は[観察設定](inspection-profiles.md)に従う。画像上限を変えて別の観察を行う場合も、新しいrunで記録する。

自動探索の実入力の記録では、既知の計測通信だけを遮断した場合も、対象への実キー入力と操作前後の状態変化をログで照合できれば、その操作の結果を記録する。通信の遮断記録も残す。

自動探索では、送信・保存・削除・認証情報などの操作と別ページへの移動を保留する。書き込みメソッドの通信、WebSocket、ページ外へのナビゲーションを制限する。これだけで任意の本番サイトの副作用を防げる保証にはしない。必要なフォーム送信などは、テスト環境の明示した経路で既存のprobeを使い、結果を追加する。iframe、closed shadow DOM、canvas等の内部、画像を省略した表示、深さや画面数の上限は、追加検査の対象として残す。

## 既知のキーボード操作を検査する

仕様や画面の調査から操作順と期待する画面状態を確認できたら、`init`で作った設定に`keyboard_checks`を追加し、`page-audit --config <設定>`で実行する。次の例は、Tabで「製品」へ移動してEnterで開き、「業務支援」まで進む部分を確認する。

```json
{
  "keyboard_checks": [
    {
      "id": "open-products",
      "name": "製品メニューを開いて業務支援へ進む",
      "criterion": "2.1.1",
      "steps": [
        {"key": "Tab", "focus": "#skip-link"},
        {"key": "Tab", "focus": "#products"},
        {"key": "Enter", "focus": "#products", "visible": "#products-panel"},
        {"key": "Tab", "focus": "#services"}
      ]
    }
  ]
}
```

`criterion`は1.4.11、2.1.1、2.1.2、2.4.3、2.4.7、2.4.11、4.1.2から選ぶ。各手順にTab、Shift+Tab、Enter、Space、Escape、上下左右の矢印キーのいずれかと、少なくとも一つの到達条件を指定する。条件には対象を一つに絞れるセレクターを使う。開いたShadow DOMでは、内側の要素を指定できる。証拠にはホストから実際のフォーカス先までを記録する。閉じたShadow DOMと、対象を宣言できないiframeは追加検査に残す。1経路は40操作までで、20経路まで指定できる。経路ごとに初期表示から始め、最初に期待と異なった操作、操作前後のフォーカス、期待結果を保存する。経路の実行は`--max-steps`の累計に含まれる。

コンボボックスでは、DOMのフォーカスが入力欄に留まったまま候補の位置が変わる。`focus`と、候補位置を表す`aria-activedescendant`の値をそれぞれ指定する。同じ方法でタブの`aria-selected`や開閉部品の`aria-expanded`も確認できる。4.1.2の経路には`attributes`条件を含め、指定したDOM属性の結果として読む。

```json
{
  "key": "ArrowDown",
  "focus": "#city",
  "visible": "#options",
  "attributes": [
    {"selector": "#city", "name": "aria-expanded", "equals": "true"},
    {"selector": "#city", "name": "aria-activedescendant", "equals": "osaka"}
  ]
}
```

`attributes`の`equals`は文字列で指定する。要素が存在し、属性がなくなったことを確かめるには`null`を指定する。選択後のテキスト入力欄は`"value": {"selector": "#city", "equals": "大阪"}`で現在の値を照合できる。検査結果に観察した値が残るので、テストデータを使う。

iframeの出入りを確認するには、経路の `frame` に例として `{"selector":"#dialog-frame","url":"https://example.test/dialog.html"}` を指定する。直接の子で同じオリジンの文書を一つ宣言できる。設定の対象範囲にある実際の文書URLを指定する。

- キーを押す前のフォーカスが子文書内にある手順に `"input_frame": "#dialog-frame"` を指定する。省略時は親文書へ届いた実キーを確認する。
- キーを押した後の条件を子文書内で確認する手順に `"frame": "#dialog-frame"` を指定する。省略時は親文書の条件を確認する。子文書からEscapeで閉じて親に戻る手順なら、`input_frame` だけを指定する。
- 宣言した子文書や実際の入力先を確認できない場合は判定を保留する。別オリジン、アクセスできないsandbox、リダイレクトによる移動はこの経路の対象外。

リンクを実行する経路では、同じオリジンかつ対象範囲内の絶対URLを`destination`に指定できる。最後のEnter又はSpaceで指定した文書へのGET移動を許可し、到達したURLとその手順の表示条件を照合する。指定外への移動、リダイレクト、確認できない入力や更新は判断保留として扱う。

結果はページ別の機械検査に追加され、期待と異なる場合はHTML・Excelの「自動検出した問題」に操作と箇所が出る。例えば、Escapeだけで閉じられなかった場合は、指定した離脱経路の問題として報告する。キーボードトラップの判定には、別の離脱手段とその案内も確認する。

## フォーカス枠と隣接色を測る

1.4.11で、サイトが指定したフォーカス枠を調べる場合は、`keyboard_checks`の最終Tab又はShift+Tabに`focus_contrast: true`を指定する。例えば、初期表示から最初のTabで`#save`に届く場合は次のように書く。

```json
{
  "keyboard_checks": [{
    "id": "save-focus-light",
    "name": "明るい背景の保存ボタン",
    "criterion": "1.4.11",
    "steps": [{"key": "Tab", "focus": "#save", "focus_contrast": true}]
  }]
}
```

操作後や別テーマの背景も確認するときは、そこへ至る手順を含めて経路を追加する。同じセレクターでも経路ごとに実際の隣接色を測る。主文書にある角の丸くない単一の要素で、実キー入力によって外側に現れるか変化する、不透明な単色の実線`outline`が対象。四辺の直線部分と、そのすぐ外側の画素を取り出し、隣接色がそろえば3:1と比較する。複数色、重なり、切り取り、対象に届かなかった経路は判定を保留する。

この設定は`machine`でも使える。指定経路に限って枠周辺を1枚保存し、標準の画像設定と枚数上限はそのまま使う。PNGの解析には`requirements-analysis.txt`のPillowが必要。HTMLの「1.4.11 フォーカス枠のコントラスト」とJSON・Excelの機械検査で、経路、対象、測定値又は保留理由、証拠を確認できる。未指定の背景や状態は別に確かめる。

## キー入力前後のフォーカス表示を比べる

2.4.7では、`keyboard_checks`の最終操作に `"focus": "#subject", "focus_images": true` を指定し、主文書の同じ対象を比較する。キー入力の前後で、表示領域・スクロール位置・対象の矩形とフォーカスを記録する。画面外、位置の変化、対象の差し替えなどで比較できない場合は、取得できた画像と理由を残す。

検査モードにかかわらず `--screenshots all` を選び、画像上限に2枚分の空きを確保する。HTML・Excelの「フォーカスの画像証拠」には画像と操作ログへのリンクが出る。画像取得の成否からフォーカス表示の適否は判定しない。

## フォーカス先が覆われる状態を調べる

2.4.11を設定するときは、`keyboard_checks`の最終操作に `"focus": "#save", "unobscured": true` を指定する。その前にバナーなどを開く操作が必要なら、同じ経路の先行手順に加える。実際のキー入力で対象に到達した時点の矩形、ビューポート、前面要素を調べる。同じDOMにある、不透明な要素による全体の覆いを確認できれば問題として記録する。前面に一部でも見えることが確認できれば、その状態の測定を通過とする。

画面外・切り取り・透明な重なり・iframe等、測定範囲では前後関係と描画を確定できない状態は保留する。対象に到達しなかった場合も保留する。ユーザーが開いたバナーをフォーカスを進めずに閉じられるかは別に確認する。画像をすべて取得する設定では、予算の範囲内で測定直後の画面も保存する。

## ホバーで表示された内容を調べる

1.4.13の対象となるトリガーと追加表示を把握していれば、`hover_checks`に指定する。各セレクターは主文書内の要素を一つに絞る。経路を20件まで指定でき、各環境で初期表示から始まる。

```json
{
  "hover_checks": [
    {"id": "price-tip", "name": "料金の追加表示", "trigger": "#price", "popup": "#details"}
  ]
}
```

ブラウザーで実ポインターを動かし、トリガーで開いた表示までの直線上を数ピクセルずつ移動して、その経路で表示が続くかを確認する。その後、ポインターとフォーカスを維持した状態でEscapeによる解除を試す。操作、入力の届いた位置、観察結果を保存する。Escapeで閉じられない結果は、別の解除手段や例外を確認するときに使う。フォーカスだけで開くパターンや指定した時間を越える表示は追加確認に残す。

同じトリガーで表示がどのくらい続くかを調べるには、経路に`"persistence_ms": 600`など、100〜3000の整数を指定する。ポインターを保持して表示の継続と、最初に消失を確認した時刻を記録する。フォーカスや表示内容が変わる場合は保留する。

## 指定した外枠のコントラストを画素で測る

初期表示で識別に必要な外枠と確認できた部品は、`border_checks`に対象を指定して測定する。

```json
{"border_checks": [{"id": "name-border", "name": "氏名の入力欄の外枠", "target": "#name"}]}
```

検査モードにかかわらず `screenshots=all` で、画像上限内に1枚を取得する。PNGの解析には`requirements-analysis.txt`のPillowを使う。4辺が同じ単色の直線枠で、周りに重なりがなく、隣接する画素も単色のときに比を求める。対象の枠に対する3:1の比較結果と測定画像を記録する。ほかの状態と境界が必要な理由も確認する。

## 指定した文字のコントラストを画素で測る

1.4.3で、初期表示の文字色と背景色を調べるときは `text_contrast_checks` に対象を指定する。各セレクターは主文書内の要素を一つに絞る。最大20対象を指定できる。

```json
{
  "text_contrast_checks": [
    {"id": "notice", "name": "予約状況の文字", "target": "#reservation-status"}
  ]
}
```

通常の `page-audit --config <設定> --mode machine` で実行できる。対象は `p`、`span`、`div`、`label` の直下にある1行のテキスト。文字色を一時的に変更し、文字の下にある実際の背景色を測る。測定用のブラウザーコンテキストで描画を安定させ、変更前と復元後の画像が一致した場合に、比を4.5:1又は大きな文字の3:1と比較する。複雑な描画、重なり、折り返し、測定中の状態変化や通信は保留する。

PNGの解析には `requirements-analysis.txt` のPillowを使う。明示した対象と環境ごとに文字周辺だけを切り出した画像を最大7枚保存する。標準の画像がoffでも計測を実行できる。HTMLの「1.4.3 文字のコントラスト」とJSON・Excelの機械検査で、対象、色、比と閾値、又は保留の理由を確認できる。達成基準の例外、操作後の状態、指定外の文字は別途確認する。

## 機械の結果と達成基準の判定

axeのWCAGタグ付きルールを実状態ごとに実行する。キーボードで候補へ到達できたか、操作を送出できたかも入力ログとともに残す。結果は「通過（機械）」「問題あり（機械）」「機械判定不能」「対象なし（機械）」として出力する。Tabで到達できなかったことだけで、代替操作のないキーボード不適合を確定しない。

自動探索で要素を一つに絞れない場合や、最後の操作の前に経路が止まった場合は「機械判定不能」とし、停止理由を表示する。最後の対象に実Tabで到達できなかった場合は、その経路の「問題あり（機械）」を表示する。操作後の表示やフォーカスが期待と一致するかは、指定したキーボード経路で確認できる。

機械検査の問題は、自動検出した問題の表から対象・状態・期待結果・観察・証拠を確認できる。機械ルールの通過だけでは、その達成基準の全条件、全対象、意味、状態を満たしたことにはならない。未判定の検査票を自動的に適合で埋めない。[ACTの判定の対応](ACT.md)と原典に従い、必要な条件を満たした証拠からrecordする。

## AI・人の判断を必要な範囲へ絞る

page-nextは、残る経路、機械結果の件数、未完了の検査票と原典・手順・その状態の機械結果を返す。まず利用可能な道具で機械検査・測定・実操作を進める。画像と代替説明の意味の対応など、自動ルールで決まらない箇所だけを内容判断へ回す。画面の観察を含め、実施した範囲を[操作調査票](visual-discovery.md)と判定へ保存する。実SRや実拡大等は既存のアダプターを使い、実施と省略を区別する。

探索中に残った項目は、追加検査の観察と証拠を用意してresolve-explorationで解消を記録できる。graph_digestはpage-nextで取得する。同じ版の項目は1件ずつ保存しても累積し、以前の解消項目を再送する必要はない。同じ項目だけを再記録しても他の項目は保持する。探索の版が変われば過去の解消記録を流用しない。キューに残った未実行の経路は、この操作では解消できない。

```json
{"graph_digest":"取得した値","resolutions":[{"item":"remainingの対象項目をそのまま指定","observed":"追加の実操作で確認した事実と範囲","evidence":["evidence/attached/対象/追加検査.json"]}]}
```

```sh
python3 scripts/audit.py resolve-exploration --run /project/run-page --file /project/resolutions.json
```

道具が使えないだけで直ちに人へ渡さず、代替手段と必要な環境を調べて実行する。人の権限や専門的な意味判断など、実際に必要な場合だけ、試した方法と具体的な残る操作を引き継ぐ。

## ページの結果を出す

```sh
python3 scripts/audit.py page-report --run /project/run-page --page-exact https://example.com/contact
```

新規の単独ページ検査では、`page` と `page-audit` の終了時に `reports/report.html`、`reports/report.xlsx`、`data/report.json` を作る。HTMLの冒頭で修正箇所、実施結果、残る確認を読む。機械ルールの結果は基準全体の判定と区別する。モードの仕様、個別の検査票、証拠のリンクは詳細から参照できる。

`page-report` で再集計すると、公開用の帳票を同じ保存先に更新する。複数ページのrunでは、個別ページの結果を `reports/pages/<ページID>/` と `data/pages/<ページID>/` に置く。元の操作ログと測定は `work/evidence/` に置く。提出する証拠パスは従来どおり `evidence/…` で、処理用JSONでは `evidence_base` が基準になる。CLIの `--run` には `--out` で指定したフォルダーを渡す。従来形式のrunでは従来の参照先と出力名を使う。

この仕組みの実行成功は、機械検査と帳票作成を終えた意味。WCAG検証完了には、予定した検査票の未実施・判断保留・未網羅、探索・画面観察、必要な読み上げ等の未確認と適合要件の確認が残っていないことが必要。状態を有限個試しただけで、任意のページの全状態を網羅したとは表明しない。
